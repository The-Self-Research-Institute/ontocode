OntoCode Desktop — Electron Guide

Everything you need to develop, build, and ship the standalone desktop app. No Docker required at runtime — all backend services start automatically inside the app.

Dev hot-reload Conversion guide Bundled JRE Build for Windows P2P Sync

Overview

OntoCode Desktop is a fully self-contained Electron application. The end user installs a single .exe / .dmg / .AppImage and gets a complete ontology editing environment — no Java, no Docker, no account required.

🖥 End User

Downloads the installer. Launches OntoCode. Everything starts automatically. Works 100% offline. Files stay on their own machine.

🛠 Developer

Runs Docker for the backend, Vite for the UI, and Electron pointed at both. React changes appear in Electron via HMR in <100 ms.

Dev Hot-Reload Workflow

In dev mode (ELECTRON_IS_DEV=1), Electron skips the bundled JAR startup entirely, connects to your Docker backend, and loads the React UI from Vite's dev server which provides full HMR. React changes appear in the Electron window in ~100 ms.

One-command start (Windows)

REM From the repo root or electron-app/
electron-app\scripts\start-electron-dev.bat

This script does three things in sequence:

  1. 1
    Start Docker backend docker compose -f docker-compose.dev.yml up -d
  2. 2
    Start Vite dev server Opens a new terminal running npm run dev in webview-src/ (port 5173)
  3. 3
    Start Electron Launches with ELECTRON_IS_DEV=1 — DevTools open automatically, no JAR startup

Manual start (three terminals)

# Terminal 1 — Docker backend
docker compose -f docker-compose.dev.yml up -d

# Terminal 2 — Vite HMR
cd ontology-vscode-extension\webview-src
npm run dev

# Terminal 3 — Electron
cd electron-app
set ELECTRON_IS_DEV=1
npx electron .

Changing Java / Spring Boot Code

Java changes need a Docker rebuild. Electron stays open — just refresh the window after the service restarts.

Rebuild only the editor service (~30-60 s)
docker compose -f docker-compose.dev.yml up -d --build ontology-editor

Then in Electron:
Ctrl+R   (refresh window)

Conversion Guide — What Changed

The web app (Docker + browser) became a desktop app (Electron + child processes). These are the specific changes made to adapt it.

1. API URL Injection

In the web app the gateway routes requests. In Electron the React app talks directly to the Spring Boot service. main.js injects the URL on page load:

// main.js — injected into every page load
mainWindow.webContents.executeJavaScript(`
  window.__DESKTOP_API_URL__ = 'http://127.0.0.1:18083';
  window.__DESKTOP_MODE__    = true;
  window.__IS_DEV__          = false;
`);

The React apiClient.ts checks window.__DESKTOP_API_URL__ and uses it when present, falling back to the normal gateway path in the browser.

2. IPC Bridge (preload.js)

Native capabilities (file picker, sync, notifications) are exposed to the renderer via Electron's contextBridge — never via nodeIntegration.

// preload.js
contextBridge.exposeInMainWorld('electronAPI', {
  openFile:      ()      => ipcRenderer.invoke('file:open'),
  saveAsFile:    (data)  => ipcRenderer.invoke('file:saveAs', data),
  syncStatus:    ()      => ipcRenderer.invoke('sync:status'),
  shareWorkspace:(opts)  => ipcRenderer.invoke('sync:shareWorkspace', opts),
  ipc:           (ch, d) => ipcRenderer.invoke(ch, d),
});

In React, always guard with window.electronAPI? so the same code works in both the browser and Electron.

3. ServiceManager

The four processes that run as Docker containers in the web app run as Node.js child_process.spawn() calls in the desktop app. Each process is:

  • Health-checked before the next one starts (TCP or HTTP poll)
  • Logged to %APPDATA%/OntoCode/logs/<name>.log
  • Stopped gracefully on quit (SIGTERM → SIGKILL after grace period)
// Startup sequence in ServiceManager.startAll()
await startMongo();    // waits for TCP :27117
await startFuseki();   // waits for HTTP /$/ping on :13030
await startEditor();   // waits for HTTP /actuator/health on :18083

Prepare Resources

Before building the installer, all backend binaries must be in resources/backend/. Run the prepare script once per release:

cd electron-app
node scripts/prepare-resources.js

The script handles each resource in order:

Bundled JRE — No System Java Required

Key point The packaged desktop app includes its own Java runtime. End users never need to install Java. The JRE is checked first by both detect-java.js and ServiceManager.js before falling back to any system Java.

How the JRE is bundled

prepare-resources.js tries two strategies in order:

  1. 1
    jlink (preferred — uses the build machine's JDK) Creates a minimal custom runtime with only the modules Spring Boot and Fuseki need. Result: ~65 MB. Fastest option, no download required. 
    # Equivalent manual command:
jlink --add-modules java.base,java.desktop,java.management,java.naming,\
  java.net.http,java.sql,java.xml,jdk.httpserver,jdk.jfr,jdk.unsupported \
  --output resources/backend/jre \
  --strip-debug --no-man-pages --compress=2
  2. 2
    Temurin 17 download (auto-fallback) If no JDK / jlink is available, downloads the pre-built Eclipse Temurin 17 JRE (~200 MB) from Adoptium's API, extracts it, and places it in resources/backend/jre/.
JRE typeSize on diskIn installer (compressed)
Full Temurin 17 JRE~200 MB~80 MB
jlink minimal~65 MB~30 MB

Package & Distribute

Build order Always run prepare-resources before dist. electron-builder packages whatever is in resources/backend/ — it does not download anything itself. 
# 1. Build Spring Boot JAR
mvn -pl ontology-editor package -DskipTests

# 2. Bundle JRE + copy all resources
cd electron-app
node scripts/prepare-resources.js

# 3. Build React SPA
#    (prepare-resources does this automatically; manual step shown for clarity)
cd ../ontology-vscode-extension/webview-src && npm run build
cd ../../electron-app

# 4. Package
npm run dist:win    # → dist-electron/OntoCode Setup x.x.x.exe
npm run dist:mac    # → dist-electron/OntoCode-x.x.x.dmg
npm run dist:linux  # → dist-electron/OntoCode-x.x.x.AppImage

CI / CD (GitHub Actions sketch)

jobs:
  build-windows:

    steps:
      - uses: actions/checkout@v4

Decentralized Sync & Share — Overview

OntoCode Desktop uses Syncthing for peer-to-peer sync. Syncthing is bundled as a binary and starts automatically. No central server, no account, no subscription required for sync.

P2P Sync

Devices sync directly over LAN or via Syncthing's community relay servers. No data passes through OntoCode servers.

Share Links

A ontocode-sync://… URL encodes your device ID + folder IDs. Send it to a collaborator by any means.

Device Pairing Flow

  Device A (Alice)                            Device B (Bob)
  ────────────────                            ──────────────────
  1. Click "Share Workspace"
  2. Select workspace folder
  3. Copy share link ──── send via email ───► 4. Click "Import Link"
                                              5. Paste link
                                              6. OntoCode adds Device A as peer
                                              7. Requests folder
  8. Accept incoming request ◄─────────────────────────────────
  ─────────────────────────────────────────────────────────────
  Sync starts automatically whenever both devices are online

Share Link Format

// Format
ontocode-sync://<base64url(JSON)>

// JSON payload
{
  "v":         1,
  "deviceId":  "ABCDE12-FGHIJ34-...",
  "folderIds": ["ontocode-a1b2c3d4"]
}
No credentials in the link The link only identifies which device and folders to request. Syncthing's TLS device certificate model handles authentication — you explicitly accept each peer.

Sync IPC API

// All calls go via window.electronAPI.ipc(channel, payload)

// Is Syncthing running?
const status = await window.electronAPI.ipc('sync:status');
// → { running: true }

// Get this device's ID
const deviceId = await window.electronAPI.ipc('sync:deviceId');
// → "ABCDE12-..."

// Share a workspace (opens folder picker)
const result = await window.electronAPI.ipc('sync:shareWorkspace', { label: 'MyOntology' });
// → { folderPath, folderId, link: "ontocode-sync://..." }

// Import a share link received from another user
const parsed = await window.electronAPI.ipc('sync:parseLink', { link });
await window.electronAPI.ipc('sync:addPeer', {
  deviceId: parsed.deviceId,
  folderId: parsed.folderIds[0],
  peerName: 'Alice',
});

// Sync progress for a folder (0–100)
const pct = await window.electronAPI.ipc('sync:completion', { folderId, deviceId });

// Pause / resume a folder
await window.electronAPI.ipc('sync:setPaused', { folderId, paused: true });
