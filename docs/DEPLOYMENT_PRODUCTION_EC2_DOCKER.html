OntoCode production on Amazon EC2 (Docker Compose only)

This runbook deploys the full OntoCode stack on a single EC2 instance using Docker Compose only. It does not use Kubernetes, EKS, or ECS task definitions. For conceptual background and Stripe live versus test keys, see Production deployment guide.

1. What you will have after this guide

  • One EC2 host running Docker with the services defined in docker-compose.production.yml (MongoDB, GraphDB, auth, gateway, ontology editor, SWRL, plugin init chain, webapp).
  • Application logs on the host under /var/log/ontocode/ (subfolders per service).
  • A single .env file on the server (not committed to git) holding secrets and URLs.

Capacity: Production compose expects meaningful RAM (GraphDB alone is capped at 8g in the file; editor up to 4g; plus MongoDB, gateway, auth, SWRL, plugin). Use an instance type with at least 16 GiB RAM as a practical minimum for a single-node production deployment, and more if many concurrent users or large ontologies are expected. EBS volume size should cover Docker images, MongoDB and GraphDB volumes, and logs.

2. Prerequisites

2.1 AWS account and EC2 instance

  • An EC2 instance in a VPC with a public or private IP, depending on how users reach the app (ALB in front is common; this guide also works with a public IP on the instance).
  • Key pair for SSH access.
  • IAM role optional (for SSM Session Manager instead of SSH if you prefer).

2.2 Security group (firewall) rules

Adjust to your security policy. Typical pattern:

PortSourcePurpose
22Your office IP / bastion onlySSH administration.
80Load balancer or 0.0.0.0/0 if no ALBHTTP gateway (compose maps host 80 to gateway).
443Same as 80HTTPS only if you terminate TLS on the instance (install nginx or Caddy in front of Docker, not covered in minimal compose).
3000Same as 80React webapp (compose publishes 3000:3000); restrict if you put the UI behind the same reverse proxy on 443 only.
8086Restrict (admin VPN) or omit from publicAuth API; often kept internal and reached only via gateway.
27017, 7200, 8083, 8084, 8087Do not open to the internetMongoDB, GraphDB, editor, SWRL, plugin — internal only.

2.3 Software on the instance

  • Docker Engine and the Docker Compose v2 plugin (docker compose, not legacy docker-compose).
  • Git to clone or pull the repository.
  • A text editor: vim, nano, or any editor you use instead of vi .env.

Example on Amazon Linux 2023 (run with sudo as needed for your AMI):

sudo dnf update -y
sudo dnf install -y git vim docker
sudo systemctl enable --now docker
sudo usermod -aG docker ec2-user
# log out and back in so group docker applies

Install Compose plugin if not bundled (check with docker compose version). On Ubuntu, use apt install docker.io docker-compose-v2 git vim or Docker’s official install instructions from Docker documentation.

2.4 Before you SSH

  • GraphDB license file available (see .env.example for GDB_LICENSE_FILE / how the GraphDB image expects the license).
  • Registry access: credentials to pull images if your DOCKER_REGISTRY is private.
  • Production Stripe live keys and live price IDs if billing is enabled.
  • A long random JWT_SECRET generated offline (for example openssl rand -base64 48).

3. Create the application directory

Use a fixed path so operators always know where the deployment lives. Example: /opt/ontocode (requires sudo to create). Alternatively use /home/ec2-user/ontocode without sudo for the directory itself.

sudo mkdir -p /opt/ontocode
sudo chown ec2-user:ec2-user /opt/ontocode
cd /opt/ontocode

Replace ec2-user with your SSH user (ubuntu on Ubuntu AMIs).

4. Get the application code

4.1 First-time clone

cd /opt/ontocode
git clone <YOUR_GIT_REPO_URL> .
# or clone into a subfolder then move files; the important part is compose and Dockerfile paths at repo root

4.2 Updates (later releases)

cd /opt/ontocode
git fetch origin
git checkout <branch-or-tag>
git pull

After git pull, review docker-compose.production.yml and .env.example for new environment variables before restarting containers.

5. Environment file

5.1 Create .env

cd /opt/ontocode
cp .env.example .env
vi .env

Use nano .env if you prefer. The file must stay on the server only; add .env to .gitignore if your fork ever removes it.

Fill every value for production. The table below maps the main groups; cross-check .env.example and any new keys in compose.

5.3 Compose-only variables

Some values are referenced only in docker-compose.production.yml (for example MONGO_ROOT_USER). Ensure every ${VAR:?} or required substitution in that file has a value in .env or defaults you accept.

6. Host log directories and permissions

docker-compose.production.yml bind-mounts log directories on the EC2 host. Create them before first up so containers do not fail creating log files.

sudo mkdir -p /var/log/ontocode/auth \
  /var/log/ontocode/gateway \
  /var/log/ontocode/editor \
  /var/log/ontocode/swrl

# Services run as root in the compose file; host dirs owned by root are typical:
sudo chown -R root:root /var/log/ontocode
sudo chmod -R 755 /var/log/ontocode

If you see permission errors in container logs when writing to these paths, verify the bind mount exists and is writable by the container user (root). As a last resort for debugging only, some teams use sudo chmod -R 777 /var/log/ontocode; tighten permissions once the root cause is fixed.

7. Start the stack

From the repository root (where docker-compose.production.yml lives):

cd /opt/ontocode
docker compose -f docker-compose.production.yml --env-file .env pull
docker compose -f docker-compose.production.yml --env-file .env up -d

Watch startup the first time:

docker compose -f docker-compose.production.yml logs -f --tail=100

Confirm all services are running:

docker compose -f docker-compose.production.yml ps

8. Verification on EC2

  • Gateway: From the instance, curl -sI http://127.0.0.1:80 (or your health path if configured).
  • Editor liveness: curl -sf http://127.0.0.1:8083/actuator/health/liveness
  • GraphDB: curl -sf http://127.0.0.1:7200/rest/repositories (do not expose 7200 publicly).
  • Webapp: Open http://<EC2_PUBLIC_DNS>:3000 or your TLS URL in a browser; confirm API calls go to the gateway URL configured in the webapp environment (ONTOCODE_API_URL in compose points at http://gateway:80 inside the Docker network, which is correct for container-to-container traffic; external users use port 80 on the host).

9. TLS on EC2 (optional but recommended)

Docker Compose alone serves HTTP on port 80. For HTTPS in front of the same host, common patterns are: install Caddy or nginx on the EC2 instance listening on 443 and proxy to 127.0.0.1:80 and 127.0.0.1:3000, or place an Application Load Balancer in front with an ACM certificate and target groups to instance ports 80 and 3000. This guide does not replace those TLS steps; they remain outside Kubernetes.

10. Ongoing operations

  • Deploy new version: git pull, adjust VERSION in .env if needed, then docker compose ... up -d again.
  • Backups: Back up Docker volumes (mongo-data, graphdb-data, graphdb-import) and /var/log/ontocode per your retention policy.
  • Disk space: Monitor EBS with CloudWatch; prune old Docker images with docker system prune only when you understand what will be removed.

11. Troubleshooting

  • Compose exits with “JWT_SECRET is required”: Export or define JWT_SECRET in .env and pass --env-file .env.
  • Cannot pull images: Run docker login <registry> on the instance for private registries.
  • GraphDB OOM or slow start: Instance too small; scale instance RAM or reduce load.
