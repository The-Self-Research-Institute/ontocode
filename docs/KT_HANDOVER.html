What is OntoCode

OntoCode is a collaborative web/IDE platform for editing OWL/RDF ontologies. Think of it as Protégé in the browser, with workspaces, role-based collaboration, version control, SPARQL/SWRL/DL-Query tooling, citation insertion (Zotero), and a plugin marketplace.

It ships in two surfaces:

  • Standalone web app — accessed at ontocode.selfresearch.org via the API at ontocodeapi.selfresearch.org.
  • VS Code extension — same UI hosted in a VS Code webview. Talks to the same backend; uses a postMessage proxy when CORS would otherwise block direct calls.

What users do here

  • Create/import OWL ontologies (.owl, .ttl, .rdf).
  • Edit class hierarchies, properties, individuals, datatypes, annotations.
  • Run a reasoner (ELK / HermiT) and SWRL rules.
  • Query with SPARQL and DL Query.
  • Insert citations from Zotero with DOI validation.
  • Collaborate with workspace members (Pro+).
  • Track changes (audit history) and merge versions.

Tech stack

Backend

Java 21 Spring Boot 3 Spring Cloud Gateway, Spring Security with JWT, Spring Data MongoDB.

Ontology engine

OWL API RDF4J Reasoners: ELK (EL), HermiT (DL). SWRL via SWRLAPI.

Storage

MongoDB for users, workspaces, projects, file metadata, GridFS for raw OWL bytes. Ontotext GraphDB for the actual triple store (one named graph per project file).

Frontend

React 18 TypeScript Vite, Tailwind, Lucide icons. Stripe Elements for card capture.

Billing

Stripe Account-level subscriptions (Model B). SetupIntent → Subscription native flow, plus a checkout-session fallback. Webhook-driven sync.

Infrastructure

Docker Kubernetes Logback rolling+gzip. Per-service rolling logs.

Runtime contract in one sentence

Every authenticated request from a client carries a JWT minted by ontology-auth; the gateway validates it, attaches user identity to downstream calls, and the editor/swrl services use that identity plus the project context (a projectId path param) to do their work against GraphDB and MongoDB.

Services overview

Service Port Owns Talks to
ontology-gateway 80 Routing, CORS, auth filter, request log. All other services.
ontology-auth 8086 Sign up / login / verify, JWT issuance, password reset, workspaces, members, invitations, Stripe customers/subscriptions, plan feature config. MongoDB, Stripe, SMTP.
ontology-editor 8083 OWL parsing, GraphDB CRUD, SPARQL, class/property/individual/annotation queries, project metadata, file storage (GridFS), citations, history, collaboration. MongoDB, GraphDB, ontology-auth (for token refresh).
ontology-swrl 8084 SWRL rule storage, parsing, execution; ELK/HermiT reasoning when triggered. MongoDB, GraphDB.
ontology-plugin-service 8087 Plugin marketplace metadata (optional in dev). MongoDB.
Why a separate auth service? The editor service talks to GraphDB and parses large OWL files; we don't want the JVM that hosts the OWL API to be in the hot path for every login. Keeping auth isolated also means the auth service can scale horizontally to handle Stripe webhook bursts without restarting heavy editor instances.

Service: ontology-gateway

Spring Cloud Gateway. Single ingress for the API. Owns CORS, route mapping, and JWT validation. Forwards to the appropriate downstream service based on path prefix.

Auth filter

The gateway extracts the Authorization: Bearer JWT, validates the signature against the shared secret, and rewrites X-User-Id / X-User-Email downstream so the editor and SWRL services don't need to re-decode the JWT for every request.

Logging

Logback rolling policy at ontology-gateway/src/main/resources/logback-spring.xml — daily + 50 MB roll, 30-day app retention, 90-day error retention, gzip on roll.

Service: ontology-auth

Owns identity, workspace membership, invitations, and Stripe billing. This is where almost every "is this user allowed to…" decision is made.

Security

JWT minted with jjwt. Custom JwtAuthenticationFilter in the auth service for endpoints that the gateway doesn't already authenticate (e.g. webhook handlers, public verification endpoints). Password reset tokens are single-use and time-bounded by security.tokens.password-reset-hours.

Where billing logic lives. All Stripe API calls happen in StripeService. The webhook handler in SubscriptionController turns Stripe events into local DB writes via WorkspaceService.syncWorkspacesToOwnerPlan. If you're chasing a "plan didn't propagate" bug, that's the function to read first.

The GraphDB naming convention

Each opened file is assigned a derived id: ontologyProjectId = `${initialProjectId}--${fileId}`. The named graph URI is http://ontocode.org/project/{ontologyProjectId}. SPARQL queries are scoped via FROM <graphURI> injection inside GraphDBDatasetService.

Reasoners

ELK is the default (fast, EL profile). HermiT is available as a fallback for full DL but expensive on large ontologies. Triggering a reasoner runs in ReasonerService; results are written back into a parallel inferred named graph so the asserted graph is never mutated.

Service: ontology-swrl

Hosts SWRL rule storage and execution. Uses SWRLAPI on top of OWL API. Rules are stored in MongoDB and re-applied to the project's GraphDB graph when triggered. Reasoning passes write inferences to the inferred named graph.

  • Rule lifecycle: create → parse (SWRLAPI) → save → run-on-demand or scheduled.
  • Logging: dedicated SWRL_FILE appender; rule traces don't pollute the main log.

Service: ontology-plugin-service

Optional. Stores plugin manifests for the marketplace. The frontend's PluginMarketplace + pluginLoader read from this service and dynamically import plugin bundles.

Frontend: webview architecture

Single Vite-built React SPA at ontology-vscode-extension/webview-src. Loaded by both the standalone web build and the VS Code webview panel.

State conventions

  • Persistent UI state (selected file, expanded nodes) lives in sessionStorage via small helpers in utils/sessionCleanup.ts so the user can refresh without losing context.
  • Route history is also persisted in sessionStorage (useRouter) so browser back/forward works after refresh.
  • API state mostly lives in the components that need it; we haven't adopted React Query. The trade-off is duplication, not chaos — it's been intentional to keep the bundle small.

URL mapping

See config/routes.ts. In a hosted browser the URL uses pathname routing (/billing, /projects/:projectName). In the VS Code webview the protocol is vscode-webview:// which can't have a real pathname, so we fall back to hash routing. The detection is at the top of routes.ts: 

const shouldUseHashRouting = (): boolean => {
  const protocol = window.location.protocol;
  return protocol.startsWith('vscode-webview') ||
         protocol.startsWith('vscode-webview-resource');
};

Navigation rules

  • currentRoute is derived from app state in App.tsx useMemo. The render branch then matches on currentRoute.view.
  • navigateTo({ view }) calls onRouteChange, which flips state booleans (e.g. setShowBillingPage(true)); on the next render currentRoute recomputes and the URL is pushed.
  • Order matters. The currentRoute useMemo evaluates branches top-down. Billing and other "modal" views need to outrank workspace-selection so they aren't immediately overwritten.

Auth context

contexts/AuthContexts.tsx is the single source of truth for "who is the logged-in user". It exposes: 

{
  user: User | null,
  loading: boolean,
  needsWorkspaceSelection: boolean,
  login, signup, logout,
  forgotPassword, resetPassword, resendVerification, verifyEmailAndLogin,
  selectWorkspace, switchWorkspace,
  updateSubscriptionPlan, updateUserRole,
  refreshPermissions,
  sessionExpiredMessage,
}

The JWT carries workspaceId and subscriptionPlan, so when those change server-side (e.g. owner upgrades, member is added) we call refreshPermissions() which hits /api/auth/refresh and swaps the token. Components downstream see the new user.subscriptionPlan on the next render.

API client

services/apiClient.ts is a singleton with two transport modes:

  1. Direct HTTP (axios) — used in the standalone web app.
  2. VS Code proxy — when running inside a VS Code webview, CORS prevents direct calls to the backend, so we proxy through the extension host via postMessage. Each call gets a unique request id; the extension answers with another postMessage and the client resolves the matching promise.

Detection happens once at instantiation: 

private isVSCode = typeof window !== 'undefined' &&
  !!window.vscode &&
  !(window as any).__ONTOCODE_CONFIG__?.IS_WEB_EXTENSION &&
  !(window as any).__ONTOCODE_BROWSER_BRIDGE__;
Two flags, two escape hatches. IS_WEB_EXTENSION is set when the same SPA runs in the Browser "extension" packaging. __ONTOCODE_BROWSER_BRIDGE__ is set by a Chrome bridge used in dev. Both force direct HTTP even when window.vscode is present.

Errors

Both transports normalize failures into ApiError with { status, data, code }. Always read error.status / error.data, not error.response.* — that's an axios-shape that doesn't survive the VS Code proxy.

Identity rules

  • Account = User. Stripe customer is created per-user. One account, one paid subscription.
  • Workspace.ownerId is the User who owns the workspace. The owner's account plan is reflected onto the workspace via syncWorkspacesToOwnerPlan.
  • Workspace.members is an embedded list. Each entry has its own role (OWNER / ADMIN / MEMBER / VIEWER).
  • Project.members is project-scoped, separate from workspace members. Used for project-level sharing.

GraphDB & named graphs

Ontotext GraphDB is the actual triple store. We use a single shared repository, with one named graph per (project, file) pair: 

graph URI = http://ontocode.org/project/{projectId}--{fileId}

Lifecycle

  1. User uploads a file → ProjectImportService parses it (OWL API) and SPARQL-INSERTs it into the named graph.
  2. Reads happen via GraphDBDatasetService (with a FROM <graph> clause) or the in-memory ProjectRepoCache.
  3. Mutations go through OntologyMutationService which emits SPARQL UPDATE and immediately invalidates Spring caches and the per-project memstore.
  4. Reasoner output goes to a parallel {graph}-inferred named graph.

Token lifetime

  • JWT is short-lived (~15 minutes). The frontend silently calls /api/auth/refresh when needed (e.g. after plan changes via refreshPermissions).
  • Tokens are stored in localStorage (web) and persisted in VS Code secret storage via saveAuthToken postMessage.
  • Logout clears both, plus session-storage caches via clearSessionCache().

Email verification

Signup creates an unverified user, sends a token-bearing link. The /verify-email route on the SPA processes the token via verifyEmailAndLogin which both verifies and signs the user in.

Workspace lifecycle

  1. First login → no workspace yet. The SPA renders WorkspaceSelection which prompts the user to create one.
  2. Create workspace → POST /api/workspaces. Owner becomes the workspace owner with role OWNER. Workspace inherits the user's account plan.
  3. Invite members → POST /api/invitations generates a token and sends an email. Acceptee can sign up if needed and gains membership.
  4. Owner upgrades plan → StripeService updates the Stripe subscription; webhook fires; WorkspaceService.syncWorkspacesToOwnerPlan propagates the new plan to every workspace they own. Members' JWTs refresh on the next 15-second poll (see bug #38).
  5. Owner cancels → workspace billing status flips to CANCELED; collaborationEnabled is turned off; access remains until currentPeriodEnd.
  6. Workspace delete → only the owner; blocked while a paid subscription is active within the validity window (see WorkspaceController.deleteWorkspace).

Billing & subscriptions

Model B: account-level billing

There is exactly one Stripe customer per user account, and at most one active subscription per account. Workspaces inherit the account's plan via WorkspaceService.syncWorkspacesToOwnerPlan. There is no per-workspace Stripe customer. This is why the "Read-only billing view" notice was removed — there is no workspace-vs-account distinction at the billing layer.

Two subscription paths

  1. Native flow (preferred):
    1. Frontend asks for a SetupIntent: POST /api/billing/setup.
    2. Stripe Elements collects the card; stripe.confirmSetup returns a setupIntentId.
    3. Frontend confirms: POST /api/billing/confirm-subscription which calls StripeService.createSubscriptionAfterSetup — creates or updates the subscription with the saved card.
  2. Checkout session (legacy fallback): StripeService.createCheckoutSession opens Stripe-hosted Checkout. Used when SetupIntent isn't available.

Trial gating

Stripe doesn't track trial-eligibility per customer. We do, via two columns on User: 

private boolean hasUsedFreeTrial = false;
private LocalDateTime firstSubscriptionAt;

Both create paths in StripeService only call setTrialPeriodDays when hasUsedFreeTrial == false && firstSubscriptionAt == null. The flag is set atomically with the subscription create (so a double-submit can't grant two trials).

Webhook handling

Stripe events arrive at POST /api/billing/webhook. Signature is verified against stripe.webhook-secret. We listen for:

  • customer.subscription.created → set local subscription record, sync workspaces.
  • customer.subscription.updated → propagate plan / status / period end changes.
  • customer.subscription.deleted → mark canceled, disable collaboration on owned workspaces.
  • invoice.payment_succeeded / invoice.payment_failed → email + status update.

Ontology editing flow

File open path (the "fast path")

  1. User clicks a file → Dashboard.handleLoadProjectFile.
  2. Compute ontologyProjectId = `${initialProjectId}--${fileId}`.
  3. Skip if already loaded: projectId === ontologyProjectIdCheck && classHierarchy.length > 0.
  4. Probe GraphDB: GET /api/ontology/{id}/graphdb/check?fileName=…. If it returns exists: true, graphSize > 0 we skip re-uploading and call fetchData.
  5. fetchData queries metadata, top-level classes, hierarchies, etc. in parallel.
  6. Otherwise: full upload from MongoDB → SPARQL INSERT → poll status → fetchData.

Add Class / Subclass / Sibling UX

The toolbar in EntityHierarchy.tsx has two buttons per entity-tab:

  • Sibling / top-level (Rows3 icon) — contextual: with no selection it creates at the top (under owl:Thing / owl:topObjectProperty / etc.); with a selection it creates a sibling.
  • Subclass / sub-property (CornerDownRight icon) — always creates a child of the selection. Without a selection it surfaces a notification ("select a class first").

Buttons are never disabled — see bug #46 for why that was wrong.

Citations & DOI validation

Two entry points: the Zotero picker (CitationPickerDialog) and the manual entry dialog (ManualCitationDialog). Both go through one validation service: services/doiValidationService.ts → GET /api/citations/validate-doi.

Authoritative validation

Pure regex isn't validation. The backend resolves the DOI via doi.org with content negotiation and reads CSL JSON from the registrar (Crossref / DataCite): 

GET https://doi.org/{doi}
Accept: application/vnd.citationstyles.csl+json
  • 200 → DOI exists; record returned. Compare against the citation (title, journal, year) using fuzzy token-overlap (≥0.7 coverage).
  • 404 → unregistered. Hard fail.
  • 5xx → resolver outage. Don't cache, retry available.

Three result states

StateMeaningUX
okvalid + relevantinsert silently with the registrar-canonical DOI string
warnvalid but registrar metadata disagreesshow registrar's title/journal/year; second click on "Insert anyway" overrides
faildoi.org returned 404insert disabled; user must correct or skip

Zotero field name footgun

Zotero's Web API uses data.DOI (uppercase) for journal articles, books, theses, etc. Lowercase data.doi appears in some legacy translators. The extra free-text field often holds DOI: 10.x/y. utils/doi.ts:extractDoiFromZoteroData handles all three.

Real-time collaboration

Available on Pro and Enterprise plans (see bug #49). WebSocket-based. CollaborationContext on the frontend opens a socket when a project is loaded; CollaborativeEditService on the editor backend fans out edit events to other connected members.

  • Edit events: class added/renamed, property added, axiom changed.
  • Each edit carries the originator's user id; the local UI ignores its own echoes.
  • Cursor position is broadcast in CollaborativeCursor.
  • Reconnect is automatic; on reconnect we trigger a fetchData with forceRefresh to resync.

Logging

Every Java service ships with a logback-spring.xml using a size+time rolling policy with gzip compression on roll.

  • Default log dir: ./logs (override LOG_DIR env var).
  • App log: rolls daily and at 50 MB, 30-day retention, 1 GB total cap.
  • Error log (WARN+): 90-day retention, kept longer than app logs.
  • Compressed archives go to logs/archive/<svc>-{app|error}-YYYY-MM-DD.N.log.gz.
  • cleanHistoryOnStart=true ensures retention is enforced on boot.

Bug history (recent fixes)

A condensed log of recently-fixed issues with the why. When a guard or pattern looks weird, check here before deleting it.

#36 / #37 — Free plan could export

useSubscription.canAccessFeature returned true for any key not in SubscriptionLimits. 'hasMultipleExportFormats' wasn't defined, so it always allowed. Fix: changed the default to false and added explicit hasExport / hasMultipleExportFormats keys per plan. Code-view Copy All / Download now also gate on canExport via a prop on CodeHighlighter.

#38 — Members didn't see the new plan after owner upgrade

The 15-second workspace polling loop in ProjectDashboard only refreshed members; it didn't notice plan/status changes. Fix: extended the loop to compare subscriptionPlan / billingStatus against the last seen values and call refreshPermissions() on change.

#39 / #40 — Re-trial after cancellation

Stripe doesn't track trial eligibility per customer. Cancelling and re-subscribing granted a brand-new trial each time. Fix: added hasUsedFreeTrial + firstSubscriptionAt on User; both create paths in StripeService skip setTrialPeriodDays when either is set. The flag is set atomically with the subscription create.

#41 — Failed to load projects after cancel = forced logout

ProjectDashboard.loadData called clearCacheAndLogout() on any error. Cancellation can produce 402/403 from /api/projects/my, which dumped the user out entirely. Fix: only auto-logout on 401; otherwise show a tailored error with Retry / Switch Workspace / Manage Subscription / Log out buttons.

#42 — Cancel button shown to all members

Frontend hid no destructive billing actions for non-owners. Fix: BillingManagement now takes isOwner; backend /api/billing/cancel-workspace double-checks workspace.ownerId === user.id and returns 403 otherwise. Later refined further: billing is account-level, so the page treats the logged-in user as their own account owner unconditionally (bug #50).

#43 — File opens with 0 classes after cancel→renew

Two server-side caches survive a cancel→renew cycle without any invalidation:

  1. Spring @Cacheable on topLevelClasses / allClasses / etc., only evicted on mutations or imports.
  2. ProjectRepoCache in-memory mirror, only evicted on writes.

If anything populated the cache with empty results during the gap, that empty list is sticky. Recommended remediation (not yet implemented):

  • Add @CacheEvict on cancel and re-subscribe webhook handlers.
  • Or: refuse to cache empty results — unless = "#result == null || #result.isEmpty()".
  • Or: bust the GraphDB fast-path on detected plan transition canceled → active in the frontend.

#44 — Manage Billing button didn't navigate

showBillingPage flipped to true on click, but the currentRoute useMemo evaluated workspace-selection branch first and immediately overwrote the route. Fix: added a billing branch above workspace-selection in the useMemo, and moved the BillingManagement render block above the workspace-selection block.

#45 — Annotation property creation missing

No toolbar Add button on the AnnotationProperties tab; sub-annotation-property not supported. Fix: added Add buttons (top + sub) to EntityHierarchy.tsx; handleCreateAnnotationProperty now calls addSubPropertyOf after create when the user clicked "Add sub-property". Backend mutation is the generic addSubPropertyOf SPARQL — no Java change needed.

#46 — Class add UX

Buttons used disabled={!selectedItem} which was a silent no-op when you clicked. Binary icon for "sibling" was nonsensical. Fix: buttons are always clickable; handler shows a notification when a selection is required; Rows3 for sibling/top-level, CornerDownRight for subclass/sub-property.

#47 — Notifications invisible in the webapp

Local showNotification in Dashboard.tsx only postMessage'd to VS Code. In the standalone webapp (no window.vscode) it just console.log'd — silently. Fix: routes through notificationService.notify which uses toast/Notification API on web and postMessage in VS Code.

#48 — Billing route piggybacking on workspace state

Same root cause as #44. Added a dedicated view: 'billing' branch in currentRoute with showBillingPage in deps. URL is /billing (or #/billing in VS Code).

#49 — Collaboration disabled on Pro

PLAN_LIMITS.pro.hasAdvancedCollaboration was false. Backend already had collaborationEnabled = true for Pro. Fix: flipped the frontend flag to true. Enterprise still differentiated by SLA / on-prem / advanced security / dedicated support / custom integrations.

#50 — Read-only billing notice was misleading

Billing is account-level. The "Only the workspace owner can change…" notice conflated account ownership with workspace ownership. Fix: removed the notice; BillingManagement always treats the logged-in user as their own account owner (isOwner=true); cancel always sends workspaceId: "" so the backend takes the account-level path.

#51 — Upgrade Plan inaccessible from account-level billing

SubscriptionPlanSelection render gate required user.isAdmin && user.workspaceId. From WorkspaceSelection or account-level billing, both are missing. Fix: relaxed to user && showSubscriptionPlan; pass empty workspaceId; auto-enable allowCurrentPlanSelection when status isn't active/trialing so users can re-pick the same plan to renew.

#52 — Logging without rotation in the gateway

Editor and SWRL had rolling configs; gateway and auth didn't. Fix: created logback-spring.xml in the missing services with the standard 50 MB / daily / gzip / 30-day policy.

Common pitfalls

  • Two run modes, one bundle. The same React build runs in browser and VS Code webview. window.vscode presence determines transport. If something works in one but not the other, that's almost always the fork to suspect.
  • Spring caches survive subscription state. Cancel/renew flows aren't an invalidation trigger. If "data is missing after renewing", suspect the cache before suspecting the data.
  • Zotero field casing. data.DOI uppercase is the canonical Zotero name. Lowercase exists too. The extra field is free text and can hold a DOI as "DOI: 10.x/y".
  • Account-level billing. Don't add per-workspace Stripe customers. Workspace plan = account plan, propagated by syncWorkspacesToOwnerPlan.
  • Trial gate is not on Stripe. Stripe will happily grant trials forever. Server-side check via hasUsedFreeTrial / firstSubscriptionAt is what stops it.
  • Route useMemo order matters. Branches evaluate top-down. Add new high-priority views (like billing) above the workspace-selection branch.
  • Don't disabled a contextual button silently. Either keep it clickable and explain via notification, or hide it. Silent disabled = "broken click" complaint.
  • API base URL. Always read via getGatewayUrl() — never hard-code. Cloud / self-hosted detection lives in config/deploymentConfig.ts.
