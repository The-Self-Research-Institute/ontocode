OntoCode — Payment testing guide

A repeatable test plan for the entire Stripe + email stack: trial, charge, fail, cancel, re-subscribe, upgrade, downgrade. Every step includes the manual click-path, the database verification query, the log line to look for, and the email subject expected in the inbox.

How to use. Run through the cases in order on the very first run — they share state. Subsequent runs can be cherry-picked. The payment-test CLI and the Stripe CLI let you skip real wall-clock time (e.g. trial reminders that would otherwise need to wait 14 days).

Scope

  • Stripe SetupIntent + Subscription native flow (preferred path)
  • Stripe Checkout fallback path
  • BillingReminderService cron — trial-ending and renewal reminders
  • Webhook events: customer.subscription.*, invoice.payment_*
  • Server-side trial gate — hasUsedFreeTrial / firstSubscriptionAt
  • Workspace plan propagation via syncWorkspacesToOwnerPlan
  • Frontend gates: Cancel button (owner-only), Update Card, Upgrade Plan, View Plans
  • All transactional emails (verification, invitation, project access) and billing emails (trial start, trial ending, payment success, payment failed, cancellation, renewal reminder)

Out of scope

  • Live Stripe production keys — use test mode only
  • Real card data — never. Use Stripe's test cards.
  • SMS / push notifications — none are wired

Prerequisites

  1. All four backend services running (gateway 80, auth 8086, editor 8083, swrl 8084).
  2. MongoDB reachable; the users and workspaces collections exist.
  3. Frontend running (webapp on :3001 or VS Code extension dev host).
  4. Stripe test secret + webhook secret set on ontology-auth: 
    STRIPE_API_KEY=sk_test_...
STRIPE_WEBHOOK_SECRET=whsec_...
stripe.trial-period-days=1     # or 14 — match what production uses
  5. SMTP credentials so emails actually send. For local dev, MailDev on :1025 catches everything without delivering, and exposes a UI on :1080.
  6. Stripe CLI logged in to the same test account: 
    stripe login
stripe listen --forward-to http://localhost/api/billing/webhook
  7. email.test-endpoints.enabled=true on auth so the admin /api/admin/test-emails/* routes work.
  8. The payment-test CLI installed: 
    cd scripts/payment-test
npm install
export MONGODB_URI="mongodb://admin:changeme123@localhost:27017/ontocode?authSource=admin"
node payment-test.js help

Test tools

  • Stripe CLI — trigger webhook events, inspect events, replay logs. See below.
  • payment-test CLI — manipulate Mongo state for time-travel testing. See below.
  • EmailTestController — admin endpoint to send any email manually: POST /api/admin/test-emails/<type> with { "to": "you@example.com" }.
  • MailDev (or Mailtrap) — local SMTP sink so emails don't actually leave the network.
  • Browser devtools / Network tab — every /api/billing/* call is visible.

Test plan

1. Sign up + email verification

PRIORITY · HAPPY PATH

1.1 Fresh signup with verification email

Steps

  1. Open the app at /signup.
  2. Submit a fresh email + password.
  3. Wait for "Welcome to OntoCode!" email; click Verify Email.

Verify

  • Mongo: users.findOne({email}).emailVerified === true
  • Auth log: 
    [REQ] POST /api/auth/signup ... -> 200
Sending verification email to: you@example.com
Verification email sent successfully to: you@example.com
  • Inbox: subject "OntoCode: Please Verify Your Email Address"

Negative cases

  • Submit existing email → 409 / "user already exists"
  • Click verify with stale token → "Verification token has expired" page
  • Skip verification, try to log in → blocked with "verify your email"

2. Trial start (Pro / Enterprise selection)

PRIORITY · HAPPY PATH

2.1 First-ever subscription receives a trial

Steps

  1. Log in. Land on SubscriptionPlanSelection (workspace-less first-time flow).
  2. Pick Professional → Continue.
  3. Stripe Elements appears. Use 4242 4242 4242 4242.
  4. Click Start Trial.

Verify

  • Mongo: 
    users.findOne({email}) → {
  subscriptionStatus: "trialing",
  subscriptionPlanName: "PRO",
  hasUsedFreeTrial: true,            // set atomically with create
  firstSubscriptionAt: ISODate(...), // set atomically
  stripeSubscriptionId: "sub_..."
}
  • Auth log: 
    Granting 1-day trial to user you@example.com (first ever subscription)
Subscription sub_... (trialing) created for user you@... / workspace ws_...
  • Inbox: "Your OntoCode Professional trial has started — 1-day free"
  • BillingManagement page renders Trial active badge.
EDGE

2.2 Enterprise = no trial

  1. From a fresh user, pick Enterprise.
  2. UI shows: "Enterprise plans are charged immediately. No trial period is available."
  3. After confirm, Mongo shows subscriptionStatus: "active" directly. hasUsedFreeTrial still set to true.

3. Trial-ending reminder

CRON

3.1 Reminder fires at 15/7/1 days before trial end

The cron is 0 0 9 * * * by default. To test without waiting, jump the user's period-end forward and either trigger the cron manually or temporarily change the cron expression.

Setup

# move the trial to end in 1 day
node payment-test.js expire-trial you@example.com 1

# (optional) temporarily run the cron every minute
# in ontology-auth/application.properties:
billing.reminder.cron=0 * * * * *
# restart auth

Verify

  • Auth log within 60s: 
    [BillingReminder] Trial ending reminder sent to alice (1 days before)
[BillingReminder] Sent 1 trial + 0 renewal reminders
  • Inbox: "Your OntoCode trial ends in 1 day — <date>"
  • Mongo unchanged (reminders don't mutate state).

Window edge cases

  • expire-trial <email> 7 → 7-day reminder fires
  • expire-trial <email> 15 → 15-day reminder fires
  • expire-trial <email> 8 → no reminder (8 isn't in the configured days)

4. Trial end → first charge

WEBHOOK

4.1 Stripe charges on day N+1, sends invoice.payment_succeeded

Skip waiting by triggering the webhook directly:

stripe trigger invoice.payment_succeeded

Verify

  • Auth log: 
    StripeWebhookController received: invoice.payment_succeeded
Invoice payment recovered for user ... — status set back to active
Sent 'Payment confirmed — OntoCode Professional' to ...
  • Mongo: subscriptionStatus: "active"
  • Inbox: "Payment confirmed — OntoCode Professional"
  • BillingManagement page → Active badge, payment history shows the new invoice.

5. Renewal reminder + charge

CRON · WEBHOOK

5.1 Reminder fires N days before period end

node payment-test.js schedule-reminder you@example.com 7 active
node payment-test.js preview-reminders

Verify

  • preview-reminders lists the user before the cron runs.
  • After billing.reminder.cron (default 09:00): renewal reminder subject "OntoCode PRO renews in 7 days on <date> — $59/month"
  • For a 1-day reminder: 
    node payment-test.js schedule-reminder you@example.com 1 active
  • To smoke-test SMTP without waiting for cron, use billing-email-test.js or POST /api/admin/test-emails/renewal-reminder.
WEBHOOK

5.2 Renewal charge succeeds

stripe trigger invoice.payment_succeeded

→ "Payment confirmed" email; currentPeriodEnd moves forward by one month.

6. Plan expiry

CRON · MONGO

6.1 Period end in the past

node payment-test.js expire-plan you@example.com
node payment-test.js show you@example.com

Verify

  • subscriptionCurrentPeriodEnd is before now on the user and owned workspaces.
  • After billing.expiry-check.interval-ms (default every 6 hours), owned paid workspaces move to EXPIRED.
  • To force the UI state immediately without waiting for the job: 
    node payment-test.js mark-expired-workspace you@example.com

7. Auto-renewal

CRON · MONGO

7.1 Auto-renew enabled, period ends within 24h

node payment-test.js set-autorenew you@example.com on
node payment-test.js schedule-autorenew you@example.com

Verify

  • User keeps autoRenewEnabled=true and a Stripe subscription id in Mongo.
  • After billing.autorenewal.cron (default 02:00), workspace period end rolls forward when auto-renew is enabled.
  • With auto-renew off, the same window should end in expiry instead of renewal: 
    node payment-test.js set-autorenew you@example.com off
node payment-test.js schedule-autorenew you@example.com

8. Payment failed

WEBHOOK · ERROR PATH

6.1 Failed renewal email + status flip

stripe trigger invoice.payment_failed

Verify

  • Auth log: 
    StripeWebhookController received: invoice.payment_failed
Invoice payment failed for user ... — status set to past_due
Sent 'Action required: OntoCode payment failed — update your card' to ...
  • Mongo: subscriptionStatus: "past_due"
  • Inbox: "Action required: OntoCode payment failed — update your card"
  • BillingManagement page → Payment failed red badge; Update Payment CTA.
RECOVERY

6.2 Update card → next charge succeeds

  1. Click Update Payment; enter 4242 4242 4242 4242.
  2. stripe trigger invoice.payment_succeeded

→ Mongo flips back to active; "Payment confirmed" email.

7. Cancel subscription

PRIORITY · HAPPY PATH

7.1 Owner cancels their own account subscription

  1. BillingManagement → Cancel Plan → Confirm Cancellation.

Verify

  • Mongo: 
    users.findOne({email}) → {
  subscriptionStatus: "canceled",
  subscriptionCanceledAt: ISODate(...),
  autoRenewEnabled: false,
  hasUsedFreeTrial: true   // never reset
}
  • Workspaces: 
    workspaces.find({ownerId}).forEach: {
  billingStatus: "CANCELED",
  collaborationEnabled: false
}
  • Inbox: "Your OntoCode Professional subscription has been cancelled"
  • BillingManagement → Done screen with "All Set!"

Body sent to backend

POST /api/billing/cancel-workspace
{ "workspaceId": "" }     // empty = account-level (Model B)
SECURITY

7.2 Member cannot cancel

  1. Log in as a workspace member (not the owner).
  2. Manage Billing page should NOT show the Cancel Plan button.
  3. Even if you POST manually to /api/billing/cancel-workspace with the owner's workspaceId, expect 403.

Auth log

[REQ] POST /api/billing/cancel-workspace ... -> 403
Only the workspace owner can cancel the subscription.

8. Re-subscribe after cancellation (no trial)

PRIORITY · TRIAL GATE

8.1 Stripe is asked to skip trial on second create

  1. From the canceled state in test 7.1, click Renew Plan.
  2. Pick the same plan; confirm with the test card.

Verify

  • Auth log: 
    Skipping trial for user you@example.com (hasUsedFreeTrial=true, firstSubscriptionAt=2026-05-04T...). Card will be charged immediately.
  • Mongo: subscriptionStatus: "active" (NOT trialing).
  • Inbox: "Payment confirmed" straight away (no "trial started").
  • Stripe Dashboard → Subscriptions → trial_end is null on this new sub.
REGRESSION GUARD

8.2 Reset the trial flag and confirm trial returns

Only useful for tests; never do this in production.

node payment-test.js reset-trial you@example.com
# now re-subscribe through the UI

→ Auth log shows "Granting 1-day trial" again; Mongo flips hasUsedFreeTrial back to true.

9. Upgrade plan (Pro → Enterprise)

PRORATION

9.1 Mid-cycle upgrade

  1. BillingManagement → Upgrade Plan → pick Enterprise.

Verify

  • Mongo: subscriptionPlanName: "ENTERPRISE"; stripeSubscriptionId unchanged (it's an UPDATE, not CREATE).
  • Workspaces: subscriptionPlan propagates via syncWorkspacesToOwnerPlan.
  • Stripe Dashboard → Subscription updated; proration line items appear on next invoice.
  • BillingManagement → price card now shows Enterprise pricing.

10. Downgrade plan

EDGE

10.1 Pro → Free at end of cycle

  1. From a Pro user, BillingManagement → Cancel Plan (treats as downgrade-to-free).
  2. After period end, status → canceled; workspace falls back to FREE limits.
EDGE

10.2 Enterprise → Pro

  1. From an Enterprise user, View Plans → pick Professional.
  2. Verify proration credit on next invoice.
  3. Members beyond the Pro cap of 10 should remain accessible until period end.

11. Workspace plan propagation to members

FRONTEND POLLING

11.1 Owner upgrades — member sees Pro within 15s

  1. Sign in as a member of a workspace whose owner is on Free.
  2. Owner upgrades to Pro in another browser.
  3. Wait up to 15 seconds — the member's ProjectDashboard polls /api/workspaces/{id}, detects the plan change, and calls refreshPermissions().
  4. Member's useSubscription hook now returns Pro; gated UI (export, collaboration) becomes enabled.

Verify

  • Browser console (member): [ProjectDashboard] Subscription state changed (FREE/ACTIVE -> PRO/ACTIVE) — refreshing permissions
  • Re-issued JWT in localStorage carries new plan claim.

12. Owner-only billing actions

SECURITY

12.1 Cancel / Update Card / Upgrade visible only to owner

BillingManagement renders Update Payment, Upgrade Plan, and Cancel Plan only when isOwner === true. From App.tsx the page always treats the logged-in user as the owner of their own account (Model B), so a non-account-holder shouldn't even reach the page from ProjectDashboard.

  • Workspace member navigates to billing → no destructive buttons.
  • Owner sees all three.
  • Direct POST as a member: 403.

Manual email triggering

Admin-gated endpoints under /api/admin/test-emails/ let you fire any email without going through the full flow. Useful for template / inbox / SMTP smoke tests.

JWT="<your-admin-jwt>"
GW="http://localhost"

curl -X POST "$GW/api/admin/test-emails/payment-failed" \
     -H "Authorization: Bearer $JWT" \
     -H "Content-Type: application/json" \
     -d '{"to":"you@example.com","planName":"PRO","amount":"$59.00 USD"}'

# index of every endpoint + body schema
curl -s "$GW/api/admin/test-emails" -H "Authorization: Bearer $JWT" | jq

The endpoint requires email.test-endpoints.enabled=true on the auth service AND a JWT with ROLE_ADMIN. Returns 404 in production where the flag is off.

Send all test emails at once

scripts/payment-test/billing-email-test.js posts to every /api/admin/test-emails/* route exposed by EmailTestController. Use it for SMTP/template smoke tests without running signup, webhooks, or cron.

cd scripts/payment-test
export AUTH_BASE_URL=http://localhost:8086
export EMAIL_TEST_ENDPOINTS_ENABLED=true   # on ontology-auth

node billing-email-test.js --to you@example.com --jwt "<admin-jwt>"

Covers verification, password reset/changed, trial started/ending, payment succeeded/failed, subscription cancelled, renewal reminder, and project access. Workspace invitation is still UI-only.

Verifying delivery

  1. Auth log line: 
    Sent '<subject>' to <recipient>
    Means JavaMail handed the message to SMTP without throwing.
  2. SMTP provider dashboard (SES / SendGrid / Mailgun) — confirms delivery and any bounces.
  3. If using MailDev locally → http://localhost:1080 to inspect rendered HTML.
  4. For real Gmail SMTP, check the Sent folder of the SMTP_USERNAME account.

If step 1 shows up but the inbox is empty, the issue is deliverability (SPF / DKIM / from-domain), not code. If step 1 doesn't appear, the trigger never fired — go back upstream (cron didn't run, webhook didn't arrive, etc.).

payment-test CLI (Mongo time-travel)

Located at scripts/payment-test/. Manipulates the users and workspaces collections so reminder / cancel / re-subscribe paths can be tested without waiting real time.

Install

cd scripts/payment-test
npm install
export MONGODB_URI="mongodb://admin:changeme123@localhost:27017/ontocode?authSource=admin"

expire-trial <email> [N=1]trialing, periodEnd = now + N days
expire-renewal <email> [N=1]active, periodEnd = now + N days

Example sessions

# view current state
node payment-test.js show alice@example.com

# fire a renewal reminder window without guessing dates
node payment-test.js schedule-reminder alice@example.com 7 active
node payment-test.js preview-reminders

# force expiry / auto-renew windows
node payment-test.js expire-plan alice@example.com
node payment-test.js schedule-autorenew alice@example.com

# simulate the cancel-then-resubscribe loop
node payment-test.js mark-canceled alice@example.com
# now go through the UI to renew
# afterwards verify the user did NOT get a new trial:
node payment-test.js show alice@example.com  # status should be 'active', not 'trialing'

# back to a clean slate for a fresh trial test
node payment-test.js reset-plan alice@example.com
node payment-test.js reset-trial alice@example.com
Use only in dev / staging. The script makes direct Mongo writes that bypass Stripe entirely. The Stripe-side state will drift if you run these against a database that's connected to a live Stripe account — only your local DB will reflect the change, and the next real webhook will overwrite your manipulation.

Cleanup after testing

  1. Revert any temp billing.reminder.cron override.
  2. Revert email.test-endpoints.enabled to false if you flipped it on.
  3. Delete the test users / workspaces created (Mongo Compass or db.users.deleteMany({email: /test\+.*@example\.com/})).
  4. In the Stripe Dashboard → Test mode → Subscriptions, cancel any lingering test subscriptions (they otherwise generate phantom renewal events forever).
  5. Stripe CLI: Ctrl+C the stripe listen session.
