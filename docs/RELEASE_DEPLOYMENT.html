Release Deployment

One script drives web, desktop, and the VS Code extension: scripts/deploy-coretopia-release.sh (Windows: scripts/deploy-coretopia-release.ps1). Flatpak is separate and manual — Flathub's own review process doesn't fit the same automated push/upload flow.

Prerequisites (once)

Create .env.deploy at the repo root (gitignored) with whichever of these the target mode/platform needs:

DEV_EC2_HOST=ubuntu@<dev-ip>
DEV_API_BASE=https://ontocodedevapi.selfresearch.org
DEV_SSH_KEY=/path/to/dev-key.pem        # optional if ssh-agent already has it

EC2_HOST=ubuntu@<prod-ip>               # prod SSH target
API_BASE=https://ontocodeapi.selfresearch.org   # defaults to this if unset
PROD_SSH_KEY=/path/to/prod-key.pem

ADMIN_USER=...                          # required for desktop installer uploads
ADMIN_PASSWORD=...

DOCKER_REGISTRY=ontocode                # defaults shown
DEV_VERSION=dev
PROD_VERSION=latest

The script runs check-jdk-prereqs.sh / check-wsl-prereqs.sh automatically and will tell you what's missing (JDK 17/21, Linux Node inside WSL, etc.) before it starts building.

Usage

./scripts/deploy-coretopia-release.sh --mode <dev|prod|all> --changes <service,...|all> --platform <web,vscode,windows,linux,mac|all>
  • --mode all runs dev and prod in parallel — no dev-first gate, so only use it once dev is already verified.
  • --changes takes any of fuseki graphdb auth gateway editor reasoner-worker swrl plugin plugin-init web, or all (which expands to the 8 app services, not the two DB containers).
  • --platform takes any of web vscode windows linux mac, or all. Each desktop platform is explicit now — there's no ambiguous desktop value that silently builds whatever the host happens to support; ask for windows, linux, or mac by name and the script fails loudly if the current host can't build that one (e.g. mac only works on a Mac host, windows needs native Windows or WSL cross-building into a Windows host).
  • All requested mode × platform combinations run in parallel as background branches, with live progress printed every 8s and a pass/fail summary at the end.

Dev deployment — quick reference, one command per platform

All five target the dev EC2 host / dev API (DEV_EC2_HOST, DEV_API_BASE from .env.deploy), tagged dev, not latest:

# Web (Docker services) — dev
./scripts/deploy-coretopia-release.sh --mode dev --changes web --platform web

# VS Code extension (.vsix) — dev
./scripts/deploy-coretopia-release.sh --mode dev --changes web --platform vscode

# Desktop — Windows .exe (run from Windows, or from WSL which cross-builds via the Windows host)
./scripts/deploy-coretopia-release.sh --mode dev --changes web --platform windows

# Desktop — Linux (AppImage/deb) — run from a Linux host or WSL
./scripts/deploy-coretopia-release.sh --mode dev --changes web --platform linux

# Desktop — macOS (.dmg) — must run on a Mac host, no cross-build
./scripts/deploy-coretopia-release.sh --mode dev --changes web --platform mac

Or combine any of them in a single call, e.g. --platform web,vscode,windows,linux builds/deploys all four to dev in parallel (from a WSL host, which can do both windows and linux at once). Swap --mode dev for --mode prod only after dev is verified — --mode all runs both with no gate in between.

Web (Docker services)

./scripts/deploy-coretopia-release.sh --mode prod --changes web --platform web
  1. build-and-push.sh builds each requested service's image (docker buildx, respects BUILD_PLATFORMS, default linux/amd64) and pushes to the registry.
  2. SSHes into the target host and runs docker compose ... up -d --pull always, then docker compose ps to confirm.
  3. Prod uses docker-compose.production.yml + docker-compose.r6i-xlarge.yml; dev uses plain docker-compose.yml.

--remote-build is a separate mode (currently only for swrl) that rsyncs the build context to the target host and builds there instead of pushing a local image — useful when the local machine shouldn't run buildx at all.

Desktop (Windows / Linux / macOS installers)

./scripts/deploy-coretopia-release.sh --mode prod --changes web --platform windows
./scripts/deploy-coretopia-release.sh --mode prod --changes web --platform linux
./scripts/deploy-coretopia-release.sh --mode prod --changes web --platform mac

Each platform is its own explicit branch (branch_desktop_windows / branch_desktop_linux / branch_desktop_mac) — no host auto-detection deciding what you get:

  • windows: on native Windows, builds npm run dist:win directly. From WSL, cross-calls into the Windows host (cmd.exe/powershell.exe) to run it there instead — both builds share electron-app/resources so this can't run in parallel with a linux build on the same box. From a plain (non-WSL) Linux or Mac host, it fails immediately with an error telling you to run it from Windows or WSL instead, rather than silently skipping.
  • linux: only runs on a Linux host (native or WSL); needs a real Linux Node/npm on PATH, not the Windows one — the script checks and tells you the exact apt-get command if it's missing. Builds via npm run dist:linux. Fails immediately on Windows/Mac hosts.
  • mac: only runs on a Mac host (npm run dist:mac — no cross-build support). Fails immediately on Windows/Linux hosts.

Each branch uploads only the installer type it actually built (windows-x64 .exe, linux-x64 .AppImage + linux-deb .deb, or mac-arm64/mac-x64 .dmg) via POST /api/downloads/upload (logs in as ADMIN_USER/ADMIN_PASSWORD first, then uploads with an explicit platform= tag — never let this default, that's caused silent version mismatches before). Each upload prints the public download URL.

Flatpak is not built or uploaded by this script — see below.

VS Code extension (OntoCode Studio)

./scripts/deploy-coretopia-release.sh --mode dev --changes web --platform vscode
  1. For --mode dev, generates ontology-vscode-extension/.env.dev-release pointing CLOUD_GATEWAY_URL/CLOUD_EDITOR_URL/CLOUD_PLUGIN_URL at DEV_API_BASE (prod uses the checked-in .env.prod-release as-is — verify it points at prod, not dev, before running this in prod mode).
  2. npm run bundle:all (webview + plugin bundles) using that env file.
  3. npm run package → produces the .vsix.

This only packages the .vsix locally — publishing it to the VS Code Marketplace (vsce publish) is a separate, manual step this script does not do.

Flatpak (Linux, via Flathub)

Not part of the script above — Flathub builds and hosts the package themselves once a submission PR is merged, so "deploying" here means keeping the submission correct, not pushing a build.

  1. Cut a GitHub Release with the Linux tarball asset (ontocode-desktop-linux-x64-v<version>.tar.gz) that the manifest's type: archive source points at, plus the packaging/linux/ desktop entry, metainfo, and icon files it fetches individually.
  2. Update org.selfresearch.OntoCode.yml (in the kkpranesh/flathub fork, branch org.selfresearch.OntoCode) if the release tag, sha256 sums, or runtime/base versions changed.
  3. Push to the fork branch — this only updates the linked PR if the PR is currently open; pushes while it's closed don't sync (verified this the hard way — see the PR history).
  4. Test locally before relying on review comments to catch it: flatpak-builder --force-clean --user --install-deps-from=flathub build-dir org.selfresearch.OntoCode.yml, then flatpak run the result and exercise the golden path.
  5. Flathub's submission-checker bot manages the PR (labels, auto-closes on an incomplete checklist) — only a maintainer can reopen a PR it closed; commenting to ask, not reopening yourself, is the only path available to a submitter.

Notes carried over from real deploys

  • Never run this concurrently with another deploy touching the same services/host — a prior race here corrupted an upload.
  • --changes all does not include fuseki/graphdb — those are data-holding containers and are deliberately excluded from the "all services" shorthand.
  • After any change to build-and-push.sh/.bat, docker-compose*.yml, or this script, update this doc to match.
