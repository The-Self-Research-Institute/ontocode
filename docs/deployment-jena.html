1. Architecture & service inventory

The platform is a Maven multi-module project. Seven Java modules, five runnable Spring Boot services — each shipped as a container image. The triplestore is Apache Jena Fuseki 5.0.0 with TDB2.

ServiceContainerPortPurpose
Gatewayontocode-gateway80Spring Cloud Gateway; routes /api/* to backends; handles CORS and WebSocket upgrades
Auth & billingontocode-auth8086Users, workspaces, JWT, Stripe webhooks, transactional email, scheduling
OWL editorontocode-editor8083Ontology mutations, Fuseki SPARQL integration, in-memory cache, GridFS file streaming
SWRL serviceontocode-swrl8084SWRL rule evaluation, reasoner integration
Plugin serviceontocode-plugin8087Plugin marketplace, manifest/binary downloads
Web appontocode-web3000React frontend

Infrastructure containers:

ContainerPurpose
ontocode-mongoMongoDB 6 — primary database (users, projects, GridFS files, billing). Single DB named ontocode.
ontocode-fusekiApache Jena Fuseki 5.0.0 — RDF triplestore using TDB2 (port 3030). Named graph store for all ontology triples.
ontocode-plugin-initOne-shot init container; seeds the plugin catalogue into MongoDB, then exits.

No GraphDB, no GraphDB init container, no license file required. Fuseki is open source and starts with no licensing step.

External dependencies you provision separately:

  • SMTP relay — Gmail App Password works for low volume; AWS SES recommended for prod (>500 emails/day).
  • Stripe — live mode account (sk_live_*).
  • Domain + TLS cert — Let's Encrypt via certbot on the host.
  • (Optional) S3 bucket — for backup snapshots.

The VS Code extension (ontology-vscode-extension/) ships through the VS Code Marketplace and runs on the user's machine. It calls the gateway at the public URL you configure here.

2. EC2 instance sizing

Fuseki with TDB2 is significantly lighter than GraphDB. This allows a smaller baseline instance compared to the previous GraphDB setup.

Tier Instance RAM Container limits total Compose override Use when
1 — Minimal t3.large 8 GB ≈ 5.5 GB docker-compose.t3-large.yml Dev/UAT, small team (< 20 users). Editor capped at 1.5 GB heap — large ontologies (>100 MB) will be slow.
2 — Standard t3.xlarge 16 GB ≈ 12 GB (no override — base production file) Recommended starting point for production. Handles ontologies up to ~3 M triples comfortably. Up to ~500 active users.
3 — Comfortable t3.2xlarge 32 GB ≈ 21 GB docker-compose.t3-2xlarge.yml Very large ontologies (>3 M triples), 500–2 000 users.
4 — High-volume r5.2xlarge 64 GB ≈ 40 GB docker-compose.r5-2xlarge.yml Multiple concurrent enterprise ontology workloads, >2 000 users.

The sizing override files set JVM_ARGS on the fuseki service automatically. You can still override per-tier heap via .env:

FUSEKI_JVM_ARGS=-Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200

Import concurrency is 1 on all tiers. TDB2 is single-writer — concurrent imports serialize at the transaction lock regardless of how many are running at the application layer.

All tiers: Ubuntu 22.04 LTS, 100 GB gp3 root volume, Elastic IP. Security Group: ports 22 (SSH, your IP only), 80 (HTTP), 443 (HTTPS). Port 3030 (Fuseki) must not be open to the internet — it has no fine-grained ACL beyond HTTP Basic auth.

All application images are pre-built and pushed to the registry. Fuseki uses the public stain/jena-fuseki:5.0.0 image — no registry auth required for it.

docker compose -f docker-compose.production.yml pull

5.2 Fuseki config file

The Compose file bind-mounts ./fuseki-config.ttl into the container. This file must exist on the server before Compose starts. Create it:

cat > /opt/ontocode/fuseki-config.ttl << 'EOF'
PREFIX fuseki:  <http://jena.apache.org/fuseki#>
PREFIX rdf:     <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs:    <http://www.w3.org/2000/01/rdf-schema#>
PREFIX ja:      <http://jena.hpl.hp.com/2005/11/Assembler#>
PREFIX tdb2:    <http://jena.apache.org/2016/tdb#>

<#service> a fuseki:Service ;
    fuseki:name                     "ontocode" ;
    fuseki:endpoint [ fuseki:operation fuseki:query  ; fuseki:name "query"  ] ;
    fuseki:endpoint [ fuseki:operation fuseki:update ; fuseki:name "update" ] ;
    fuseki:endpoint [ fuseki:operation fuseki:gsp-rw ; fuseki:name "data"   ] ;
    fuseki:endpoint [ fuseki:operation fuseki:query  ] ;
    fuseki:endpoint [ fuseki:operation fuseki:update ] ;
    fuseki:dataset <#dataset> ;
    .

<#dataset> a tdb2:DatasetTDB2 ;
    tdb2:location "/fuseki/databases/ontocode" ;
    .
EOF

This config:

  • Creates a named service ontocode accessible at /ontocode/query, /ontocode/update, /ontocode/data.
  • Persists triples to the fuseki-data Docker volume at path /fuseki/databases/ontocode.
  • Uses TDB2 (Jena's native disk-backed store). TDB2 auto-creates the database directory on first startup.

Critical: The Fuseki image declares VOLUME /fuseki in its Dockerfile. Docker anonymously mounts anything under /fuseki before bind-mounts are applied. If you mount a file at a path inside /fuseki/ before starting Compose for the first time, Docker may create a directory at that path instead of placing a file there. This causes Fuseki to fail with /fuseki/config.ttl (Is a directory).

The production Compose avoids this by mounting the config to /fuseki/config/ontocode.ttl (a sub-path that is inside the volume, so the file is created after Docker initialises the VOLUME layer). The command is overridden to --config=/fuseki/config/ontocode.ttl. See §13 for full details if you ever hit this error.

7. Start services

7.1 First boot

cd /opt/ontocode

# Pull latest images first
docker compose -f docker-compose.production.yml pull

# Start all services (t3.xlarge — default; see §2 for other tiers)
docker compose -f docker-compose.production.yml up -d

Compose starts services in dependency order:

  1. mongo — waits until healthcheck passes (~40 s on first boot)
  2. fuseki — waits until healthcheck passes (~30 s; TDB2 init on first boot takes <5 s)
  3. auth, owl-editor, swrl-service — start in parallel once their dependencies are healthy
  4. gateway, plugin-service — start after auth / editor are up
  5. plugin-init, webapp — start last

Unlike GraphDB, there is no init container for Fuseki. TDB2 auto-creates the database directory when the first write arrives. The dataset is immediately available once the service is healthy.

7.2 Check status

docker compose -f docker-compose.production.yml ps
docker compose -f docker-compose.production.yml logs -f fuseki
docker compose -f docker-compose.production.yml logs -f owl-editor

Fuseki is healthy when you see a line containing Started Fuseki in its logs and the healthcheck shows (healthy).

7.3 Verify Fuseki is serving the dataset

# Ping Fuseki
curl -sf -u admin:${FUSEKI_ADMIN_PASSWORD} http://localhost:3030/$/ping

# List datasets (should return the "ontocode" dataset)
curl -sf -u admin:${FUSEKI_ADMIN_PASSWORD} http://localhost:3030/$/datasets

# Count triples (returns 0 on a fresh install)
curl -s -u admin:${FUSEKI_ADMIN_PASSWORD} \
  --data-urlencode "query=SELECT (COUNT(*) AS ?n) WHERE { ?s ?p ?o }" \
  -H "Accept: application/sparql-results+json" \
  http://localhost:3030/ontocode/query

7.4 Auto-start on reboot (systemd unit)

Create /etc/systemd/system/ontocode.service:

[Unit]
Description=OntoCode Platform
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
User=ubuntu
WorkingDirectory=/opt/ontocode
ExecStart=/usr/bin/docker compose -f docker-compose.production.yml up -d
ExecStop=/usr/bin/docker compose -f docker-compose.production.yml down
TimeoutStartSec=300

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable ontocode

8. nginx + Let's Encrypt TLS

nginx runs natively on the host and terminates TLS. It proxies HTTPS to the gateway container on port 80 and serves the webapp on port 3000.

8.1 nginx site config

/etc/nginx/sites-available/ontocode:

server {
    listen 80;
    listen [::]:80;
    server_name ontocodeapi.example.org ontocode.example.org;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

# API gateway
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name ontocodeapi.example.org;

    # TLS config injected by certbot

    # Large OWL file uploads (up to 1 GB)
    client_max_body_size 1G;

    proxy_buffering on;
    proxy_buffer_size 16k;
    proxy_busy_buffers_size 32k;
    # 2-hour timeout for large ontology import jobs
    proxy_read_timeout 30m;

    # Stripe webhook: forward raw body for signature verification
    location /api/billing/webhook {
        proxy_pass http://127.0.0.1:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # WebSocket + SockJS HTTP fallbacks (/ws/info, /ws/*/xhr, etc.)
    # Must be a separate block — /api/ does NOT cover /ws/ paths.
    location /ws/ {
        proxy_pass http://127.0.0.1:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }

    # All other gateway paths: /api/, /assets/, /projects/, /actuator/
    location / {
        proxy_pass http://127.0.0.1:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# React webapp
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name ontocode.example.org;

    # TLS config injected by certbot

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Enable and test:

sudo ln -s /etc/nginx/sites-available/ontocode /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

9. Logging

Each Java service container mounts /app/logs into a host directory under /var/log/ontocode/<service>/. Logback writes size-rotated log files there. Fuseki writes to container stdout only (no mounted log volume).

9.1 Useful tail patterns

# All containers, streaming
docker compose -f docker-compose.production.yml logs -f

# Fuseki queries and errors
docker compose -f docker-compose.production.yml logs -f fuseki

# Editor import progress (large file imports can take minutes)
docker compose -f docker-compose.production.yml logs -f owl-editor | grep -i "import\|triple\|error"

# Application log files (more detail than container stdout)
tail -f /var/log/ontocode/auth/app.log
tail -f /var/log/ontocode/editor/app.log

# Find errors across all services
grep -i "error\|exception" /var/log/ontocode/editor/app.log | tail -50

9.2 Checking import progress by project ID

# Follow import log lines for a specific projectId
docker compose -f docker-compose.production.yml logs -f owl-editor \
  | grep "6b3e6d22-d43e-4d74-ba57-95727fdd85e7"

Expected log sequence for a successful import:

  1. SUBMIT — import request accepted, queued
  2. PROCESSING — file streamed from GridFS to disk, triples being loaded into TDB2
  3. IMPORT_COMPLETED — triples committed; triple count and duration logged
  4. METADATA_READY — class hierarchy extracted and cached

9.3 Log rotation

Logback is configured for size-and-time-based rotation (100 MB per file, 30-day history, 5 GB total cap). No additional host-level logrotate config is needed.

12. Operations & backup / restore

12.1 Restart one service

docker compose -f docker-compose.production.yml restart fuseki
docker compose -f docker-compose.production.yml logs -f fuseki

12.2 Deploy a new version

# 1. On dev machine: build and push updated image(s)
#    build-and-push.bat sindhujacoretopia 1.2.0

# 2. On EC2: pull and restart
cd /opt/ontocode
# If you tagged a specific version, set VERSION in .env first
docker compose -f docker-compose.production.yml pull
docker compose -f docker-compose.production.yml up -d

Compose recreates only containers whose image digest changed. MongoDB and Fuseki TDB2 data volumes are never touched by up -d.

12.3 Deploy a single service without touching others

docker compose -f docker-compose.production.yml up -d --no-deps owl-editor

12.4 Rollback

# Set VERSION=1.1.0 in .env, then:
docker compose -f docker-compose.production.yml pull
docker compose -f docker-compose.production.yml up -d

12.5 What to back up

IMPORTANT — never run these commands:

  • docker volume prune (may delete mongo-data and fuseki-data)
  • docker compose down -v (removes all named volumes — destroys all data)
  • docker volume rm ontocode_mongo-data or docker volume rm ontocode_fuseki-data

12.6 MongoDB backup & restore

Backup — add to crontab -e as ubuntu:

# Nightly at 03:00 UTC
0 3 * * * docker exec ontocode-mongo mongodump \
  --uri="mongodb://admin:${MONGO_ROOT_PASSWORD}@localhost:27017/ontocode?authSource=admin" \
  --out=/tmp/mongo-backup --gzip \
  && docker cp ontocode-mongo:/tmp/mongo-backup /var/backups/mongo/$(date +\%F) \
  && docker exec ontocode-mongo rm -rf /tmp/mongo-backup \
  && aws s3 sync /var/backups/mongo/ s3://ontocode-prod-backups/mongo/ \
  && find /var/backups/mongo/ -maxdepth 1 -type d -mtime +14 -exec rm -rf {} +

Restore:

# 1. Stop services that write to Mongo
docker compose -f docker-compose.production.yml stop auth owl-editor plugin-service

# 2. Copy backup into the container
docker cp /var/backups/mongo/2026-05-14 ontocode-mongo:/tmp/mongo-restore

# 3. Restore (--drop replaces existing collections)
docker exec ontocode-mongo mongorestore \
  --uri="mongodb://admin:${MONGO_ROOT_PASSWORD}@localhost:27017/ontocode?authSource=admin" \
  --drop --gzip /tmp/mongo-restore/ontocode

# 4. Clean up and restart
docker exec ontocode-mongo rm -rf /tmp/mongo-restore
docker compose -f docker-compose.production.yml start auth owl-editor plugin-service

12.7 Fuseki TDB2 backup & restore

TDB2 uses memory-mapped files and write-ahead journaling. Do not copy TDB2 files while Fuseki is running — you will get a corrupt snapshot. Always stop Fuseki first.

Backup (cold snapshot — recommended):

# 1. Stop Fuseki cleanly so WAL flushes
docker compose -f docker-compose.production.yml stop fuseki owl-editor swrl-service

# 2. Archive the volume
sudo tar -czf /var/backups/fuseki/ontocode-$(date +%F).tar.gz \
  -C /var/lib/docker/volumes/ontocode_fuseki-data/_data .

# 3. Sync to S3 (optional)
aws s3 sync /var/backups/fuseki/ s3://ontocode-prod-backups/fuseki/

# 4. Keep 14 days locally
find /var/backups/fuseki/ -name "*.tar.gz" -mtime +14 -delete

# 5. Restart
docker compose -f docker-compose.production.yml start fuseki owl-editor swrl-service

Backup (hot snapshot via Fuseki compact & copy):

# Trigger TDB2 compaction (flushes and defragments the journal)
curl -s -X POST -u admin:${FUSEKI_ADMIN_PASSWORD} \
  http://localhost:3030/$/compact/ontocode

# Then stop Fuseki and copy — as above
# Compaction reduces snapshot size and makes the copy more consistent

Restore:

# 1. Stop Fuseki and editor
docker compose -f docker-compose.production.yml stop fuseki owl-editor swrl-service

# 2. Clear existing TDB2 data and restore from archive
sudo rm -rf /var/lib/docker/volumes/ontocode_fuseki-data/_data/*
sudo tar -xzf /var/backups/fuseki/ontocode-2026-05-14.tar.gz \
  -C /var/lib/docker/volumes/ontocode_fuseki-data/_data/

# 3. Restart
docker compose -f docker-compose.production.yml start fuseki owl-editor swrl-service

# 4. Verify dataset is accessible and has data
curl -s -u admin:${FUSEKI_ADMIN_PASSWORD} \
  --data-urlencode "query=SELECT (COUNT(*) AS ?n) WHERE { ?s ?p ?o }" \
  -H "Accept: application/sparql-results+json" \
  http://localhost:3030/ontocode/query

13. Fuseki gotchas

13.1 "config.ttl Is a directory" error

This error means Docker created a directory at the path where you expected a file to be bind-mounted. It happens because the Fuseki image declares VOLUME /fuseki. When Docker initialises this VOLUME layer, it creates an empty directory tree. If a Compose bind-mount tries to place a file at a path inside /fuseki/ and the anonymous volume was initialised first, Docker creates a directory at that path instead.

Root cause diagnostic:

docker exec ontocode-fuseki ls -la /fuseki/config/
# If you see "ontocode.ttl" listed as a directory rather than a file, this has happened.

Fix (without data loss):

# 1. Stop Fuseki only
docker compose -f docker-compose.production.yml stop fuseki

# 2. Remove the container (keeps the fuseki-data volume safe)
docker rm ontocode-fuseki

# 3. Remove the stale anonymous volume that was shadowing the bind mount
#    Identify the anonymous volume (NOT fuseki-data which holds your triples)
docker volume ls | grep -v "fuseki-data\|mongo-data"
# Find the one created recently and associated with fuseki, e.g. 3abc123def45

# 4. Confirm fuseki-config.ttl exists on the host as a regular file
ls -la /opt/ontocode/fuseki-config.ttl   # must be a file, not a directory

# If it's a directory, remove it and recreate:
rm -rf /opt/ontocode/fuseki-config.ttl
# Then recreate it using the cat >> heredoc in §5.2

# 5. Restart
docker compose -f docker-compose.production.yml up -d fuseki

13.2 Dataset shows as empty after restart

TDB2 data is stored in the fuseki-data named volume at /fuseki/databases/ontocode. If Fuseki starts but returns 0 triples, check:

# Is the fuseki-data volume mounted?
docker inspect ontocode-fuseki | grep -A5 "Mounts"
# Should show fuseki-data mounted at /fuseki/databases

# Does the TDB2 directory exist?
docker exec ontocode-fuseki ls -la /fuseki/databases/ontocode/

If the mount is missing or the directory is empty, the volume was recreated. Restore from backup (§12.7).

13.3 Fuseki JVM out of memory during large imports

Very large ontologies (>5 M triples) may cause TDB2 to exceed the heap during bulk load. Signs: java.lang.OutOfMemoryError in Fuseki logs.

# Increase JVM heap in .env:
FUSEKI_JVM_ARGS=-Xmx6g -XX:+UseG1GC -XX:MaxGCPauseMillis=200

# Restart Fuseki only
docker compose -f docker-compose.production.yml up -d --no-deps fuseki

13.4 Fuseki Admin UI

Fuseki ships a web UI at http://<server>:3030. It is useful for running ad-hoc SPARQL queries and checking dataset stats. Do not expose port 3030 publicly — access via SSH tunnel:

# On your local machine:
ssh -L 13030:localhost:3030 ubuntu@your-ec2-ip
# Then open http://localhost:13030 in your browser
# Credentials: admin / FUSEKI_ADMIN_PASSWORD

14. Security checklist before going live

  • MONGO_ROOT_PASSWORD is a strong unique password — not the changeme123 default.
  • FUSEKI_ADMIN_PASSWORD is a strong password — not admin.
  • JWT_SECRET is 64+ bytes from openssl rand -base64 64. Same value across auth, gateway, and plugin services.
  • .env is mode 0600 and not committed to git — confirm with git status.
  • Port 3030 (Fuseki) is not open in the Security Group — internal Docker network only.
  • Port 27017 (MongoDB) is not open to the internet.
  • Ports 8083, 8084, 8086, 8087 are not open to the internet (accessed only through gateway on port 80/443).
  • Stripe is in live mode (keys start with sk_live_ / pk_live_ / whsec_).
  • Webhook signing secret matches what Stripe shows in the Dashboard.
  • Domain has valid TLS via certbot; auto-renew timer is enabled.
  • Security Group allows only 22 (your IP), 80, 443 to the public.
  • Admin bootstrap password rotated after first login.
  • BASE_URL in .env points to the public webapp URL, not localhost.
  • Backups are running (Mongo + Fuseki TDB2) and have been test-restored at least once.
  • Fuseki Admin UI (:3030) only accessible via SSH tunnel.
