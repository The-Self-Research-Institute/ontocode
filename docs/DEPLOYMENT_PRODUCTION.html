OntoCode production deployment guide

Production serves real users and real billing. This guide assumes Docker Compose using docker-compose.production.yml (larger GraphDB heap and memory limits than the default development compose) or an equivalent orchestration with the same services. Companion: UAT deployment guide. For a full EC2 step-by-step (prerequisites, git pull, .env, log directories, no Kubernetes), see EC2 Docker production runbook.

1. Principles

  • Secrets: Store production secrets in a secret manager or encrypted CI variables; never commit .env with live keys.
  • Network exposure: Do not publish MongoDB or GraphDB ports to the public internet. Only gateway (and optionally auth for direct admin tools) should be reachable from outside a private network, typically via TLS termination.
  • Stripe live mode: STRIPE_SECRET_KEY must be sk_live_...; price IDs must be live-mode price_... objects.
  • No destructive test tools: Do not run Mongo time-travel or billing mutation scripts from scripts/payment-test against production databases.

2. Compose and startup

docker compose -f docker-compose.production.yml --env-file .env.production up -d

Ensure host directories for log volumes exist if your compose binds /var/log/ontocode/*. Wait for MongoDB and GraphDB health before relying on editor or SWRL.

Production compose aligns with docker-compose.yml for service list and environment wiring; GraphDB uses a larger heap (6g) and an 8g container memory limit. Verify graphdb-import and graphdb-data volumes are backed up.

3. Environment variables (production)

Create .env.production from .env.example and set every value for the live domain and live integrations.

4. TLS, ingress, and upload limits

Terminate TLS at your load balancer or ingress controller. The example k8s/ingress.yaml sets large body size and long read/send timeouts for big ontology uploads; mirror those values in nginx or equivalent if you terminate outside Kubernetes.

5. Stripe production webhooks

In Stripe Dashboard (live mode), add a single webhook endpoint URL to the auth service. Subscribe only to events your application handles. Rotate STRIPE_WEBHOOK_SECRET if the endpoint is recreated. Monitor failed deliveries in Stripe and application logs.

6. Backups and disaster recovery

  • MongoDB: Scheduled logical or volume snapshots; tested restore procedure.
  • GraphDB: Repository export or data volume snapshots consistent with your RPO.
  • Configuration: Store compose files, ingress manifests, and non-secret configuration in git; store secrets separately.

7. Post-deploy verification

  1. Health endpoints for editor and dependencies.
  2. Login and session refresh through gateway.
  3. Small file upload and SPARQL query.
  4. Stripe live webhook test event (use Stripe’s “send test webhook” where appropriate, without corrupting real subscriptions).
  5. Outbound email deliverability (password reset to a controlled mailbox).

8. Upgrades

Freeze writes or announce maintenance if required. Back up databases. Deploy new images by tag. Run migration or smoke tests. Keep previous image tag for fast rollback.

9. Troubleshooting

  • 502 or timeouts on large uploads: Increase ingress and gateway timeouts together with editor ontology timeouts.
  • Webhook signature failures: Wrong STRIPE_WEBHOOK_SECRET or request not reaching auth (path must be /api/billing/webhook).
  • Email links wrong host: Fix BASE_URL and redeploy auth.
