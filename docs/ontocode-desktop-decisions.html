OntoCode Desktop

Architecture and Product Decisions for Client Review  ·  Prepared May 2026

1. Executive Summary

OntoCode is adding a desktop product positioned as a Protégé-equivalent: file-based, fully offline by default, plugin-extensible, and free at the entry tier. The existing OntoCode Cloud (web application plus backend services) remains the paid collaborative product, equivalent to WebProtégé.

The desktop product is intentionally decoupled from the cloud product. Users can move work between them by exporting and importing OWL files, but there is no live sync between products in v1. This positioning keeps the desktop simple, gives OntoCode a wider top-of-funnel for academic and individual users, and protects the existing cloud revenue model.

Strategic advantage
The cloud backend (OWLAPI, HermiT, Fuseki, SPARQL/SWRL/Fuzzy plugins) is already built. Desktop v1 is primarily a packaging and distribution problem, not a feature development problem. This significantly compresses the engineering timeline.

2. Background & Positioning

Protégé is the dominant desktop OWL editor: free, open source, Java-based, plugin-driven, file-based, and developed at Stanford. WebProtégé is its collaborative sibling — a web application for shared editing. The two products coexist with light interop (export/import of OWL files); they do not live-sync.

OntoCode mirrors this dual-product model:

  • Free desktop tier widens the user funnel. Academic and individual users who would otherwise install Protégé get a more modern alternative.
  • Paid cloud tier remains the primary revenue driver. Collaboration is the differentiator.
  • Plugin ecosystem becomes a long-term moat. OntoCode's faster, easier-to-build-for plugin platform is a real competitive lever over Protégé's OSGi system.
  • No conflict with the existing cloud business — desktop operates in a different mode (single user, offline) and converts users to cloud when they need collaboration.

3. Architecture & Product Decisions (Q1–Q16)

Q1. Which desktop framework should we build on?

The framework decision shapes the entire technical stack. The core trade-off is code reuse from the existing React webview-src/ vs bundle size, performance, and native feel.

OptionProsCons
Electron + JVM sidecar Recommended Reuses entire React codebase and existing Java OWL code unchanged. Team already knows JS + Java. Mature auto-update (electron-updater). Largest ecosystem. Bundle ~250 MB (Chromium + JRE). Higher memory. Two runtimes to debug.
Tauri (Rust + system webview) Tiny bundle (~10–15 MB). Low memory. Modern security model. Rust learning curve. System webviews differ across platforms. Cannot reuse Java OWL code.
Native (Qt / MAUI / Avalonia) Best raw performance. Genuine OS feel. Full UI rewrite. 5–10× the engineering effort. Different skill set.
JVM + JavaFX Reuses Spring Boot/OWLAPI directly. JavaFX UI is dated. Hard to match modern React polish.
Why Electron + JVM sidecar wins for OntoCode
The JVM sidecar pattern (same as VS Code bundling language servers) lets the existing OWL Editor service run as a local process instead of in Docker. The React UI remains unchanged. No code is thrown away — this is a repackaging, not a rewrite.

Q2. Where does OWL/RDF data live on disk?

OptionProsCons
File-based (.owl/.ttl as source of truth) + embedded cache Recommended Sync-friendly with every external tool (Git, Dropbox, Syncthing). Portable, human-readable. Matches Protégé mental model exactly. Cache rebuilds automatically. Cache invalidation logic. Two layers to keep consistent.
Embedded triple store only Fast queries. Efficient storage. Binary store — Git/Dropbox cannot merge it. User loses Protégé compatibility.
SQLite-only Single-file. Mature engine. RDF does not map cleanly to relational. SPARQL-to-SQL is hard.

Q3. Which reasoner(s) should ship with the desktop?

OptionProsCons
HermiT free; ELK + Pellet behind Pro license Recommended Clean free-vs-paid line. Free tier matches Protégé capability. Pro offers measurable performance and capability uplift (ELK: fast OWL EL; Pellet: better SWRL). Pellet licensing needs negotiation with Stardog. ELK only covers OWL EL profile.
HermiT only Already integrated. No additional work. No paid differentiation. Slower than Pellet on some workloads.
No reasoner, plugins only Smallest bundle. Useless out of the box. Reasoning is a core feature.

Q4. What is the on-disk workspace concept?

OptionProsCons
Workspace folder with ontology + sidecar files Recommended Each workspace = a folder: ontology.owl, queries/, rules/, history/. Portable as a zip. Maps cleanly to the existing cloud Workspace model. Slight learning curve. Users must share the folder, not just the .owl.
No workspaces, Protégé-style Minimal concept overhead. Matches Protégé exactly. No place for saved queries, SWRL rules, or change history alongside the ontology.

Q5. What is the UI approach?

OptionProsCons
Reuse webview-src/ React UI as-is in v1 Recommended Zero UI work. Day-one feature parity with web app. Same developer team. Inherits web app awkwardness on desktop. Long-term divergence pressure.
Fork and adapt for desktop Native menus, file dialogs, multi-window, keyboard shortcuts. Two versions to maintain. Risk of divergence.
New native UI Optimal desktop UX. Multi-window, real menu bars. Massive engineering effort. Disconnects from web app.

Q6. How does the plugin system work on desktop?

OptionProsCons
Port existing Plugin Service (Node.js) as sidecar Recommended Same plugin ecosystem on web and desktop. Plugins built once run on both. Existing SPARQL/SWRL/Fuzzy plugins port unchanged. Sandboxing already in place. Larger bundle (~30 MB extra). Plugin sandbox security needs review for desktop threat model.
JS plugins inside Electron renderer No sidecar needed. Simpler architecture. Plugins can crash the UI. Full DOM access by default.
WASM plugins Sandboxed, language-agnostic, fast. Ecosystem does not exist yet. No third-party plugins on day one.

Q7. What is the licensing and pricing model?

OptionProsCons
Freemium with paid Pro features Recommended Direct revenue from desktop. Predictable model (Sublime Text, JetBrains, Obsidian). Clear free-vs-paid line. Adds licensing complexity. License-file infrastructure required.
Completely free, open source Maximum reach. Community contributions. Strong academic adoption. No direct revenue from desktop.
Paid only Highest revenue per user. Lowest adoption. Most users default to Protégé rather than pay.

Q8. How is the license enforced?

OptionProsCons
Signed Ed25519 license file, offline verification Recommended Works fully offline. No phone-home. User-friendly: drag the file in once. Public key embedded in app does verification. 1-year subscription, 30-day grace period on expiry. License files can be shared. Need to handle expiry and renewals.
Online activation, account-tied Hard to share. Real account on file. Requires internet for activation. Phone-home behaviour many users dislike.
No DRM, contract terms only Zero infrastructure. Easy to pirate. Only works with enterprise customers.

Q9. Which platforms at launch?

Recommendation: Windows + macOS + Linux at launch
Linux is critical for the academic OWL user base — the most influential early adopters and reviewers. Excluding Linux at launch risks a hostile reception from Protégé power users.

Each platform adds installers, code-signing certificates, CI pipeline configuration, and ongoing testing load. AppImage for Linux in v1; packages (.deb, .rpm) and Snap/Flatpak for later releases.

Q10. How does the desktop update itself?

OptionProsCons
Built-in auto-update + manual download fallback Recommended Users always on latest version. Security patches reach them quickly. Enterprise can pin versions via manual download. Need to host an update server and signed update manifests.
Manual update only No server needed. Users lag versions. Hard to push security fixes quickly.

Q11. What is the cloud boundary?

OptionProsCons
Zero integration in v1 (separate products) Recommended Cleanest model. Each product has its own identity. Matches Protégé vs WebProtégé exactly. No coupling. Users moving between products lose in-progress work (drafts, queries, history) unless they re-export.
Server-mediated async sync (v1.x) Reuses existing cloud backend. Works async — devices need not be online simultaneously. Natural paid feature. Requires cloud account (counter to "fully offline" baseline). Infrastructure cost grows with sync volume.
Full live sync Best UX. Cloud and desktop are interchangeable. Significant engineering. Couples the two products tightly.

Q12. What is the first-launch user experience?

Recommendation: Optional local display name — no account required
One small prompt asking "What should we call you?" gives change-tracking a name to display. No password, no email, no account. If the user skips it, edits are attributed to "Anonymous." Matches Protégé's zero-friction model while adding minimal personalisation.

Q13. What file format strategy do we adopt?

Recommendation: Native OWL formats + workspace folder with sidecar files
The .owl / .ttl file is the ontology — fully compatible with Protégé and every other OWL tool. Sidecar files in the workspace folder carry OntoCode-specific metadata (saved queries, SWRL rules, change history) that other tools ignore. Sharing the workspace means sharing the folder; sharing just the ontology means sharing the .owl file.

Q14 deep-dive: how identity works

Identity = Cloud account (email/JWT), not the license file

The Pro license file (Ed25519 signed) proves only that the user has paid for Pro features — it is verified offline against the embedded public key. It contains the user's email and a userId, but it does not drive sync.

Sync identity = OntoCode Cloud account. The user signs in with email + password. The JWT issued by the Auth Service is what ties Desktop A and Desktop B to the same account. The userId in the license file is matched against the JWT claim to confirm the Pro entitlement is for this account.

Sharing with another user works like Google Drive: the workspace owner explicitly shares the workspace with another user's email address. That user sees it in their "Shared with me" list on their own desktop.

Q14 deep-dive: sync is user-driven, not automatic

Nothing syncs without an explicit user action
Sync never starts silently. Two deliberate clicks gate entry: Desktop A must click "Enable Sync" on the workspace. Desktop B must click "Download Workspace". This makes the trust boundary clear and avoids surprises.

Q14 deep-dive: Step 1 — Initial Bootstrap (Desktop B gets the workspace for the first time)

  1. User signs into OntoCode Cloud on Desktop A (email + password → JWT).
  2. User clicks "Enable Sync" on the workspace in Desktop A's UI.
  3. Desktop A uploads the full .owl file + all sidecar files (queries/, rules/, history/) to cloud storage (MongoDB GridFS). Writes WorkspaceSync metadata (projectId, ownerUserId, GridFS fileId, snapshotTimestamp T0).
  4. Cloud stores the snapshot. Sets DeviceSyncState for Desktop A with cursor = T0.
  5. User signs into OntoCode Cloud on Desktop B (same account, or invited email). Sees the workspace listed under "Available Workspaces".
  6. User clicks "Download Workspace" on Desktop B.
  7. Desktop B downloads the full .owl + sidecars from GridFS. Creates local workspace folder. Records DeviceSyncState cursor = T0.

Desktop B is now at the same state as Desktop A was at T0. Incremental sync (below) keeps them in step going forward.

Q14 deep-dive: Step 2 — Incremental Sync (ongoing)

  1. User makes edits on Desktop A. Each edit is written to a local DraftChange row with syncedToServer = false.
  2. A background worker (or user taps "Sync Now") POSTs to POST /api/ontology/changes/sync with the pending DraftChange list.
  3. Server validates the JWT, applies the changes, writes canonical OntologyChange rows, updates DeviceSyncState for Desktop A.
  4. Desktop B comes online (hours or days later). On launch (or "Sync Now") it calls GET /api/ontology/changes?projectId=X&since=T0.
  5. Desktop B replays the returned events into its local Oxigraph/TDB2 cache. Updates its DeviceSyncState cursor to the latest timestamp.

Backend additions required: 2 new endpoints, 3 new MongoDB collections (WorkspaceSync, DeviceSyncState, MergeConflict), 2 new fields (DraftChange.syncedToServer, Workspace.syncMode). Estimated effort: 4–6 weeks original / 2–3 weeks AI-assisted.

Q15. How do we resource the desktop development?

Recommendation: Same team for first 3–6 months
Knowledge stays in one team. Code reuse is natural because the same developers write both products. After MVP ships, evaluate whether to spin up a dedicated desktop team. With AI-assisted development (see Section 6), a single developer can match the throughput of a 2–3 person team on coding tasks.

Q16a. How does installation work? (Single-click, no Docker, no Java required)

Single-click installer — user double-clicks one file, app opens. Nothing else to install.

Electron already bundles Chromium + Node.js. The JVM sidecar (Spring Boot JAR) is bundled with a minimal JRE created via jlink (~50 MB), so the user does not need Java installed. The Plugin Service runs inside Electron's existing Node.js runtime — no separate Node install. Docker is not used at all in the desktop product.

How the JVM sidecar starts

Electron's main process spawns the JVM sidecar as a child process using Node's child_process.spawn():

const jrePath = path.join(process.resourcesPath, 'jre', 'bin', 'java')
const jarPath = path.join(process.resourcesPath, 'sidecar', 'owl-editor.jar')
const sidecar = spawn(jrePath, ['-jar', jarPath, '--server.port=18080'])
// React UI talks to http://localhost:18080 via window.API_BASE_URL

When the user closes the app, Electron kills the child process. No ports are exposed externally. No services run when the app is closed.

Q16. How do we version and release?

Recommendation: Independent versioning — Desktop 1.x, Cloud 2.x
Each product ships when ready. Different release cadences are natural (desktop has no server migration concern; cloud requires coordinated deploys). Date-based sub-versioning for hotfixes is acceptable within a major version.

6. Implementation Timeline with AI-Assisted Development

How AI compresses — and doesn't compress — this project

AI coding assistants (Claude Code, Copilot) accelerate pattern-based code generation significantly, but they do not compress infrastructure bureaucracy or novel architectural problems. The distinction is critical for estimating this project.

What AI accelerates (40–60% faster):

  • Java entity/repository/controller boilerplate — a new MongoDB entity takes minutes, not hours (demonstrated in this session)
  • React UI components and TypeScript wiring
  • Config files, build scripts, package.json
  • Connecting known patterns (the cloud backend patterns already exist)
  • Debugging — AI can trace execution paths across large codebases quickly

What AI does NOT compress:

  • Apple Developer Program + notarization — account setup, App Store Review, waiting periods
  • Windows code-signing — EV certificate acquisition takes 1–5 business days minimum
  • Electron + JVM IPC design — first-time complex cross-process communication; needs careful architecture
  • Auto-update server — hosting, CDN, manifest signing
  • Pellet licensing negotiation with Stardog
  • Performance testing with large ontologies (GO: 44K classes, SNOMED CT: 350K)

Existing head start — what is already built

OntoCode already has the hardest parts
OWLAPI + HermiT reasoning, the full React UI, the Plugin Service, and all three plugins (SPARQL, SWRL, Fuzzy Ontology) already exist and work in production. Desktop v1 is primarily packaging and distribution, not feature development. This is a significant advantage over a greenfield build.
