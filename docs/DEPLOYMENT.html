1. Architecture & service inventory

The platform is a Maven multi-module project. Seven Java modules, five of which are runnable Spring Boot services — each shipped as a container image:

ServiceContainerPortPurpose
Gatewayontocode-gateway80Spring Cloud Gateway; routes /api/* to backends; handles CORS
Auth & billingontocode-auth8086Users, workspaces, JWT, Stripe webhooks, transactional email, scheduling
OWL editorontocode-editor8083Ontology mutations, GraphDB integration, in-memory SPARQL cache
SWRL serviceontocode-swrl8084SWRL rule evaluation, reasoner integration
Plugin serviceontocode-plugin8087Plugin marketplace, manifest/binary downloads
Web appontocode-web3000React frontend

Infrastructure containers:

ContainerPurpose
ontocode-mongoMongoDB 6 — primary database, single DB named ontocode
ontocode-graphdbOntotext GraphDB — RDF triplestore (port 7200)
ontocode-graphdb-initOne-shot init container; creates the ontocode repository if it doesn't exist
ontocode-plugin-initOne-shot init container; seeds plugin catalogue

External dependencies you provision separately:

  • SMTP relay — Gmail App Password works for low volume; AWS SES recommended for prod (>500 emails/day).
  • Stripe — live mode account (only key you have is sk_live_*).
  • Domain + TLS cert — Let's Encrypt via certbot on the host.
  • (Optional) S3 bucket — for backup snapshots.

The VS Code extension and webview frontend (ontology-vscode-extension/) is not deployed to EC2; it ships through the VS Code Marketplace and runs on the user's machine, calling the gateway at the public URL you set up here.

2. EC2 instance sizing

Choose an instance tier and apply the matching Compose override file (§7). All tiers run the same services — only JVM heaps, GraphDB heap, and container memory limits change.

Tier Instance RAM Container limits total Compose override Use when
1 — Minimal t3.large 8 GB ≈ 6.8 GB docker-compose.t3-large.yml Dev/UAT, small team (< 20 users), budget-constrained. Editor capped at 1.5 GB heap — large ontologies may be slow.
2 — Standard t3.xlarge 16 GB ≈ 13.5 GB (no override — base file) Recommended starting point for production. Up to ~500 active users.
3 — Comfortable t3.2xlarge 32 GB ≈ 23 GB docker-compose.t3-2xlarge.yml Large ontologies (> 1 M triples), concurrent heavy imports, 500–2 000 users.
4 — High-volume r5.2xlarge 64 GB ≈ 45 GB docker-compose.r5-2xlarge.yml Multiple concurrent enterprise ontology workloads, > 2 000 users, 3 parallel imports.

3. Prerequisites — install on the EC2 box

SSH in as ubuntu and run as sudo where indicated.

3.1 Base OS

sudo apt update && sudo apt upgrade -y
sudo apt install -y curl wget gnupg lsb-release ca-certificates \
                    software-properties-common unzip jq
sudo timedatectl set-timezone UTC

Always run servers in UTC. Every timestamp in logs and cron expressions assumes this.

3.2 Container runtime

# Add the official apt repository
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /usr/share/keyrings/docker-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/docker-archive-keyring.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Allow ubuntu user to run containers without sudo
sudo usermod -aG docker ubuntu
newgrp docker   # apply without logout

# Verify
docker version
docker compose version

3.3 Node.js 20 (only needed for the ops scripts in scripts/)

curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs
node -v   # v20.x

3.4 nginx + certbot (TLS)

sudo apt install -y nginx certbot python3-certbot-nginx

Configuration is in §8. TLS issuance is also in §8.

4. Pull images from the registry

All service images are pre-built and pushed to the registry. On the EC2 box you only pull — no build tooling required.

docker login   # authenticate with your registry credentials

# Compose will pull automatically on first up (see §7),
# but you can pre-pull to confirm access and cache images now:
docker compose -f docker-compose.production.yml pull

Images pulled by Compose:

ImageBuilt from
ontocode-graphdbDockerfile.graphdb
ontocode-authDockerfile.auth
ontocode-gatewayDockerfile.gateway

ontocode-swrlDockerfile.swrl
ontocode-pluginDockerfile.plugin
ontocode-plugin-initDockerfile.plugin-init

Building images (dev machine only): each Dockerfile has a corresponding entry in build-and-push.bat. Run the script on your dev machine to build for linux/amd64 + linux/arm64 and push to the registry. On the server, always deploy by pulling — never build on the server.

5. Deployment layout

/opt/ontocode/
├── docker-compose.production.yml   # the Compose file you'll run
├── .env                            # secrets + config (mode 0600, NOT in git)
└── scripts/                        # ops and payment-setup scripts

Set this up:

sudo mkdir -p /opt/ontocode
sudo chown ubuntu:ubuntu /opt/ontocode
cd /opt/ontocode

# Clone the repo (or scp just the compose file and scripts folder)
git clone https://github.com/The-Self-Research-Institute/ontocode.git .

# Create log directories that containers will mount into
sudo mkdir -p /var/log/ontocode/{gateway,auth,editor,swrl,plugin}
sudo chown -R ubuntu:ubuntu /var/log/ontocode

6. Environment configuration (.env)

Copy the example and fill in real values. This file is read by Compose at startup — secrets never live in the repo or in image layers.

cp .env.example .env
chmod 0600 .env
nano .env   # or your preferred editor

Required values to set before first boot:

# --- Database ---
MONGO_ROOT_USER=admin
MONGO_ROOT_PASSWORD=<CHOOSE-STRONG-PASSWORD>
MONGODB_DATABASE=ontocode

# --- JWT (generate once, share across auth + gateway + plugin services) ---
# Generate: openssl rand -base64 64 | tr -d '\n'
JWT_SECRET=<paste openssl rand value here>

# --- Public URLs ---

# --- Admin bootstrap (used once at startup if no admin exists) ---

# --- Mail ---
EMAIL_FROM=noreply@example.com

SMTP_PORT=587
SMTP_USERNAME=<AWS_SES_SMTP_USER>
SMTP_PASSWORD=<AWS_SES_SMTP_PASS>

# --- Stripe (LIVE keys — no test mode in prod) ---
STRIPE_SECRET_KEY=sk_live_xxxxxxxxxxxxxxxxxxxxxxxx
STRIPE_PUBLISHABLE_KEY=pk_live_xxxxxxxxxxxxxxxxxxxxxxxx
STRIPE_WEBHOOK_SECRET=whsec_xxxxxxxxxxxxxxxxxxxxxxxx   # set after §10 webhook setup

GRAPHDB_REPOSITORY=ontocode

Defaults for scheduling and storage limits are already sane in .env.example; override only if you need to.

7. Start services

7.1 First boot

Pick the command matching your instance tier (§2). The first file is always docker-compose.production.yml; the second file overrides only the memory limits and JVM heap sizes for that tier.

cd /opt/ontocode

# Pull latest images first
docker compose -f docker-compose.production.yml pull

# --- t3.large (Tier 1 — 8 GB) ---
docker compose -f docker-compose.production.yml -f docker-compose.t3-large.yml up -d

# --- t3.xlarge (Tier 2 — 16 GB, default recommended) ---
docker compose -f docker-compose.production.yml up -d

# --- t3.2xlarge (Tier 3 — 32 GB) ---
docker compose -f docker-compose.production.yml -f docker-compose.t3-2xlarge.yml up -d

# --- r5.2xlarge (Tier 4 — 64 GB) ---
docker compose -f docker-compose.production.yml -f docker-compose.r5-2xlarge.yml up -d

Compose starts services in dependency order:

  1. mongo — waits until healthcheck passes
  2. graphdb — waits until healthcheck passes (up to ~3 min on first boot)
  3. graphdb-init — one-shot: creates the ontocode repository if missing, then exits
  4. auth, owl-editor, swrl-service — start in parallel once their dependencies are healthy
  5. gateway, plugin-service — start after auth / editor are up
  6. plugin-init, webapp — start last

7.2 Check status

docker compose -f docker-compose.production.yml ps
docker compose -f docker-compose.production.yml logs -f auth
docker compose -f docker-compose.production.yml logs -f owl-editor

7.3 Auto-start on reboot (systemd unit)

Create /etc/systemd/system/ontocode.service:

[Unit]
Description=OntoCode Platform
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
User=ubuntu
WorkingDirectory=/opt/ontocode
ExecStart=/usr/bin/docker compose -f docker-compose.production.yml up -d
ExecStop=/usr/bin/docker compose -f docker-compose.production.yml down
TimeoutStartSec=300

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable ontocode

8. nginx + Let's Encrypt TLS

nginx runs natively on the host and terminates TLS. It proxies HTTPS traffic to the gateway container on port 80 and serves the webapp on port 3000.

8.1 nginx site config

/etc/nginx/sites-available/ontocode:

server {
    listen 80;
    listen [::]:80;
    server_name ontocodeapi.selfresearch.org ontocode.selfresearch.org;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

# API gateway
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name ontocodeapi.selfresearch.org;

    # TLS config injected by certbot

    client_max_body_size 1G;

    proxy_buffering on;
    proxy_buffer_size 16k;
    proxy_busy_buffers_size 32k;
    proxy_read_timeout 30m;

    # Webhook signature verification needs the raw, untransformed body.
    location /api/billing/webhook {
        proxy_pass http://127.0.0.1:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket support for STOMP collab + cursor channels
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

# React webapp
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name ontocode.selfresearch.org;

    # TLS config injected by certbot

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Enable + test:

sudo ln -s /etc/nginx/sites-available/ontocode /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

8.2 Let's Encrypt cert

sudo certbot --nginx -d ontocodeapi.selfresearch.org -d ontocode.selfresearch.org \
             --non-interactive --agree-tos -m ops@selfresearch.org --redirect
sudo systemctl status snap.certbot.renew.timer

Certbot auto-installs a systemd timer that renews every 60 days.

9. Logging

Each service container mounts /app/logs into a host directory under /var/log/ontocode/<service>/. Logback inside the container writes structured, size-rotated log files there. Container stdout is also captured by the container runtime's logging driver.

9.1 Useful tail patterns

# All containers, streaming
docker compose -f docker-compose.production.yml logs -f

# One service only
docker compose -f docker-compose.production.yml logs -f auth

# Errors across all services (host-side log files)
grep -i "error\|exception" /var/log/ontocode/auth/app.log

# Application log file (more detail than container stdout)
tail -f /var/log/ontocode/auth/app.log

# Find a specific user's activity
grep "user@example.com" /var/log/ontocode/auth/app.log

# Webhook events received
docker compose -f docker-compose.production.yml logs auth \
  --since 1h | grep -i webhook

9.2 Log rotation

Logback is configured for size-and-time-based rotation (100 MB per file, 30-day history, 5 GB total cap). No additional host-level logrotate config is needed — the containers manage their own log files in the mounted volume.

10. Stripe setup

10.0 How pricing works — read this first

There are two independent layers of pricing that must always stay in sync:

LayerEnv varsWhat it controls
Stripe charge STRIPE_PRICE_PRO_MONTHLY, STRIPE_PRICE_PRO_YEARLY, STRIPE_PRICE_ENTERPRISE_MONTHLY, STRIPE_PRICE_ENTERPRISE_YEARLY Stripe Price IDs (price_xxx). The actual dollar amount a customer is charged. Defined inside Stripe when the price was created. This is real money.
Display price PLAN_PRO_MONTHLY_PRICE, PLAN_PRO_ANNUAL_DISCOUNT_PERCENT, PLAN_ENTERPRISE_MONTHLY_PRICE, PLAN_ENTERPRISE_ANNUAL_DISCOUNT_PERCENT Numbers shown on the pricing page. Read from .env on every auth container startup and written into the plan_feature_configs MongoDB collection. Does not affect what Stripe charges.

Rule: whenever you change prices, always update both layers together. The setup-stripe-prices.js script does this — it creates the Stripe prices and prints the complete .env block covering both layers.

Stripe prices are immutable. You cannot change a price's amount once created. Running the script with a new amount creates a new price (with a new ID). Archive old prices in the Stripe Dashboard once all subscribers have migrated.

10.1 Install the Stripe node SDK

cd /opt/ontocode/scripts/payment-setup
npm install

10.2 Script — register the webhook endpoint

scripts/payment-setup/setup-stripe-webhook.js does the following:

  1. Connects to Stripe with sk_live_*.
  2. Lists existing webhook endpoints; if one already points at your URL it prints the existing metadata and adds any missing event types (idempotent).
  3. Otherwise creates a new endpoint with the exact event types StripeWebhookController handles.
  4. Prints the whsec_* signing secret.

Run once (idempotent):

cd /opt/ontocode/scripts/payment-setup
STRIPE_SECRET_KEY=sk_live_xxx node setup-stripe-webhook.js \
  https://ontocodeapi.selfresearch.org/api/billing/webhook

Copy the printed whsec_* into STRIPE_WEBHOOK_SECRET in .env.

10.3 Script — create products and prices

scripts/payment-setup/setup-stripe-prices.js accepts your pricing inputs and does everything:

  • Creates Pro and Enterprise products in Stripe if they don't exist (idempotent, keyed by metadata).
  • Creates the 4 prices (monthly + yearly for each plan). Yearly = monthly × 12 × (1 − discount/100), rounded to the nearest dollar.
  • Prices are keyed by amount — running with a different amount creates a new price instead of reusing the old immutable one.
  • Prints a complete .env block with both the Stripe price IDs and the matching display pricing vars.

Run it with your pricing:

cd /opt/ontocode/scripts/payment-setup
STRIPE_SECRET_KEY=sk_live_xxx node setup-stripe-prices.js \
  --pro-monthly 29 \
  --enterprise-monthly 99 \
  --annual-discount 17

10.4 Changing prices later

Run the script again with the new amounts — it will create new Stripe prices and print a new .env block:

STRIPE_SECRET_KEY=sk_live_xxx node setup-stripe-prices.js \
  --pro-monthly 39 \
  --enterprise-monthly 129 \
  --annual-discount 20
  1. Paste the new .env block (both price IDs and display vars) into .env.
  2. Restart auth: docker compose -f docker-compose.production.yml up -d --no-deps auth
  3. Existing subscribers keep their old prices automatically (Stripe does not change existing subscriptions).
  4. When no active subscribers remain on the old prices, archive them in Stripe Dashboard → Products → [plan] → [old price] → Archive.

12. Operations

12.1 Restart one service

docker compose -f docker-compose.production.yml restart auth
docker compose -f docker-compose.production.yml logs -f auth

12.2 Deploy a new version

# 1. On your dev machine — build and push the updated image(s):
#    build-and-push.bat sindhujacoretopia 1.2.0

# 2. On EC2 — pull and restart (substitute your tier override if not t3.xlarge):
cd /opt/ontocode
# If you tagged a specific version, update VERSION in .env first
docker compose -f docker-compose.production.yml pull
docker compose -f docker-compose.production.yml up -d
# or with override: docker compose -f docker-compose.production.yml -f docker-compose.t3-2xlarge.yml up -d

Compose recreates only containers whose image digest changed. Mongo and GraphDB data volumes are never touched.

To deploy a single service without touching the rest: docker compose -f docker-compose.production.yml up -d --no-deps auth

12.3 Rollback

# Pin the previous version in .env: VERSION=1.1.0
docker compose -f docker-compose.production.yml pull
docker compose -f docker-compose.production.yml up -d

12.4 What to back up

WhatWhereContainsMust back up?
MongoDB datamongo-data Docker volumeUsers, workspaces, projects, billing, email logs, Stripe eventsYes — primary database
GraphDB datagraphdb-data Docker volumeAll ontology RDF triples, named graphs, versionsYes — ontology store
.env file/opt/ontocode/.envAll secrets, Stripe keys, JWT secretYes — unrecoverable if lost
nginx config/etc/nginx/sites-available/ontocodeVirtual host, TLS configRecommended
Docker imagesRegistry (sindhujacoretopia/*)Application binariesNo — always rebuildable from source
Log files/var/log/ontocode/Application logsOptional — useful for audit

Do not back up Docker images. They are reproducible artifacts — rebuild from source and push to the registry. Saving image tarballs wastes storage and goes stale. The registry is the source of truth for images.

12.5 MongoDB backup & restore

Backup — add to crontab -e as ubuntu:

# Nightly at 03:00 UTC
0 3 * * * docker exec ontocode-mongo mongodump \
  --uri="mongodb://admin:MONGO_PASSWORD@localhost:27017/ontocode?authSource=admin" \
  --out=/tmp/mongo-backup --gzip \
  && docker cp ontocode-mongo:/tmp/mongo-backup /var/backups/mongo/$(date +\%F) \
  && docker exec ontocode-mongo rm -rf /tmp/mongo-backup \
  && aws s3 sync /var/backups/mongo/ s3://ontocode-prod-backups/mongo/ \
  && find /var/backups/mongo/ -maxdepth 1 -type d -mtime +14 -exec rm -rf {} +

Restore:

# 1. Stop services that write to Mongo
docker compose -f docker-compose.production.yml stop auth owl-editor plugin-service

# 2. Copy backup into the container
docker cp /var/backups/mongo/2026-05-14 ontocode-mongo:/tmp/mongo-restore

# 3. Restore (--drop replaces existing collections)
docker exec ontocode-mongo mongorestore \
  --uri="mongodb://admin:MONGO_PASSWORD@localhost:27017/ontocode?authSource=admin" \
  --drop --gzip /tmp/mongo-restore/ontocode

# 4. Clean up and restart
docker exec ontocode-mongo rm -rf /tmp/mongo-restore
docker compose -f docker-compose.production.yml start auth owl-editor plugin-service

12.6 GraphDB backup & restore

Backup via REST API (no downtime needed):

# Trigger a backup snapshot via GraphDB REST API
curl -X POST http://localhost:7200/rest/repositories/ontocode/export \
  -H "Accept: application/zip" \
  --output /var/backups/graphdb/ontocode-$(date +%F).zip

# Sync to S3
aws s3 sync /var/backups/graphdb/ s3://ontocode-prod-backups/graphdb/

# Keep 14 days locally
find /var/backups/graphdb/ -name "*.zip" -mtime +14 -delete

Backup via volume snapshot (simpler, requires brief stop):

# Stop GraphDB cleanly so all WAL pages flush
docker compose -f docker-compose.production.yml stop graphdb

# Archive the volume contents
sudo tar -czf /var/backups/graphdb/ontocode-$(date +%F).tar.gz \
  -C /var/lib/docker/volumes/ontocode_graphdb-data/_data .

# Restart
docker compose -f docker-compose.production.yml start graphdb

Restore:

# 1. Stop GraphDB
docker compose -f docker-compose.production.yml stop graphdb owl-editor swrl-service

# 2. Clear the existing volume and restore from archive
sudo rm -rf /var/lib/docker/volumes/ontocode_graphdb-data/_data/*
sudo tar -xzf /var/backups/graphdb/ontocode-2026-05-14.tar.gz \
  -C /var/lib/docker/volumes/ontocode_graphdb-data/_data/

# 3. Restart
docker compose -f docker-compose.production.yml start graphdb owl-editor swrl-service

# 4. Verify repository is accessible
curl -sf http://localhost:7200/rest/repositories/ontocode/size

# Encrypt and push to S3 (never store secrets in plaintext)
openssl enc -aes-256-cbc -pbkdf2 -in /opt/ontocode/.env \
  -out /tmp/env-encrypted.bin -k "CHOOSE_STRONG_PASSPHRASE"
aws s3 cp /tmp/env-encrypted.bin s3://ontocode-prod-backups/config/env-$(date +%F).bin
rm /tmp/env-encrypted.bin

# Restore
aws s3 cp s3://ontocode-prod-backups/config/env-2026-05-14.bin /tmp/env-encrypted.bin
openssl enc -d -aes-256-cbc -pbkdf2 -in /tmp/env-encrypted.bin \
  -out /opt/ontocode/.env -k "CHOOSE_STRONG_PASSPHRASE"

rm /tmp/env-encrypted.bin

13. Security checklist before going live

  • MONGO_ROOT_PASSWORD in .env is a strong unique password — not the changeme123 default.
  • JWT_SECRET is 64+ bytes from openssl rand -base64 64. Same value used across auth, gateway, and plugin services.
  • .env is mode 0600 and not committed to git — confirm with git status.
  • Stripe is in live mode (keys start with sk_live_ / pk_live_ / whsec_).
  • Webhook signing secret matches what Stripe shows in the Dashboard.
  • Domain has valid TLS via certbot; auto-renew timer is enabled.
  • Security Group allows only 22 (your IP), 80, 443 to the public; 7200 (GraphDB) only to your office IP.
  • Admin bootstrap user (ADMIN_EMAIL) password rotated after first login.
  • BASE_URL in .env points to the public webapp URL, not localhost.
  • Stripe Dashboard webhook shows recent successful deliveries.
  • Backups are running (Mongo + GraphDB) and have been test-restored at least once.
